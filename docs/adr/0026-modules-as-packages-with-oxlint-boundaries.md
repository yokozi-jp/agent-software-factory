# ADR 0026: モジュールは packages/ の Nx project にし、方向は package.json の依存で、層は Oxlint の no-restricted-imports で止める

サンプル機能 (経費精算) はモジュラーモノリスにし、機能ごとのモジュールに分けます。エージェントが逆向きの import や深い import を書いても、`vp check` (pre-commit と CI) で止まるようにします。道具と配置は [モジュール境界と禁止 API の検査の道具を決める](https://github.com/yokozi-jp/agent-software-factory/issues/145) の解決コメントで決め、[Issue #179](https://github.com/yokozi-jp/agent-software-factory/issues/179) で入れました。モジュールの間の方向を lint から package.json の依存に移し、override と fixture をモジュールごとから層ごとにしたのは [Issue #303](https://github.com/yokozi-jp/agent-software-factory/issues/303) です。

## ルール

- **配置**: モジュールは `packages/` の直下に、1つずつ Nx project (pnpm workspace の package) として置きます。申請は `packages/claim`、承認は `packages/approval`、締めは `packages/closing`、モジュールが共有するコードは `packages/shared-kernel` です。モジュールの境界の検出力の fixture は、モジュールの形をした `packages/module-fixtures` に置きます (下の「検出力」)。`db`、`hr-system`、`i18n`、`logging`、`telemetry` は、外部の道具を包む共有 package の「ドライバ」で、`domain` と `infrastructure` の層を持ち、モジュールのうち `infrastructure` だけが import します (`apps/*` の入口も、組み立てのために import します)（[ADR 0054](0054-drivers-with-domain-and-infrastructure-layers.md)）。UI の部品は、モジュールでも `shared-kernel` でもない共有 package の `packages/ui` に置きます。これは例外で、`moduleOrder` に入れず、層と `exports` の規則を変えます ([ADR 0034](0034-shared-ui-package.md))。各モジュールの中の `packages/<module>/events` は、そのモジュールが外へ送るイベントのスキーマを置く入れ子の package で、これも例外です。モジュールではないので、`moduleOrder` に入れず、役割の tag (`type:` の次元) を付けません。path (`packages/<module>/events`) で見分けます。`exports` は `"."` だけで、依存は `zod` と `shared-kernel` だけです。pnpm の workspace には `packages/*/events` で入り、Nx では別の project になります。置く理由と依存の規則は [ADR 0046](0046-review-split-from-claim-and-events-in-sender-package.md)、実装は [Issue #409](https://github.com/yokozi-jp/agent-software-factory/issues/409) で入れました。`apps/api` は入口のファイルと、`app.ts` (middleware を並べ、route の sub-app とモジュールの route を付けるだけ) と、HTTP の部品 (`src/http/`。下の「HTTP の部品と Hono の import」) を持つ薄い入口にし、モジュールを `workspace:*` の依存として持ちます。
- **package の役割の tag と登録**: `packages/*/package.json` のすべてに、`nx.tags` で役割の tag を `type:` の次元でちょうど 1 つ付けます ([Issue #552](https://github.com/yokozi-jp/agent-software-factory/issues/552))。Nx は tag を `次元:値` の形で `package.json` の `nx.tags` に書くので、その書式に合わせました。`scope:` のような別の次元は後から足せます。
  - **役割の値**: `type:module` (申請、承認、締め)、`type:fixtures` (`packages/module-fixtures`)、`type:shared-kernel`、`type:ui` ([ADR 0034](0034-shared-ui-package.md))、`type:driver` (`db`、`hr-system`、`i18n`、`logging`、`telemetry`。[ADR 0054](0054-drivers-with-domain-and-infrastructure-layers.md)) の 5 つです。ドライバは ADR 0054 と `GLOSSARY.md` の用語に合わせ、`util` とは呼びません。`db` はドライバの 1 つで、別の役割にしません。
  - **検査**: repo-policy (`roles.ts` の `packagesHaveOneRole`) は、`type:` の tag がない package、2 つ以上ある package、表にない値の tag (`type:modul` など) を止めます。ほかの次元の tag は数えません。events の package (`packages/<module>/events`) は、今までどおり path で見分け、`type:` の tag を付けません。
  - **規則は tag から求める**: 層と `lint-effect` を持つのは `type:module` と `type:fixtures`、`moduleOrder` に入るのは `type:module`、workspace のどの package にも依存しないのは `type:module` 以外の役割です。例外の `db` は、モジュールに `devDependencies` だけで依存します ([ADR 0038](0038-db-package.md))。名前の一覧は規則の側に置きません。
  - **名前で引く例外**: package ごとに違う `exports` の形は `modules.ts` の `ownExports` に、ドライバごとに違う `exports` と置き場 (`tools`、`places`) は、ルートの `drivers.json` に、名前で書きます。`type:driver` の package が `drivers.json` にない、`drivers.json` にある package が `type:driver` でない、のどちらも repo-policy が止めます (`driversAreTagged`)。これがないと、新しいドライバは層と入口と Effect の検査の外に黙って置かれます。
  - **登録**: `packages/db` の型の生成の対象 (`moduleSchemas`、`packages/db/src/testing/types.ts`) は、`type:module` の package の名前から求めます。repo-policy (`modules.ts` の `modulesAreRegistered`) は、`type:module` の package が `moduleOrder` にあること、`moduleOrder` の名前がどれも `type:module` の package であること、`apps/api/package.json` の `dependencies` に `workspace:*` で入っていること、route を持つモジュール (`src/http/route/` にファイルがある) の `<name>Router` を `apps/api/src/app.ts` が `.route()` で付けていることを確かめます。route を持たないモジュールは `app.ts` に書きません: 使わない import は何もしないためです ([Issue #554](https://github.com/yokozi-jp/agent-software-factory/issues/554))。モジュールの DB は登録しません。api の入口が 1 つの `app_user` の pool を `ManagedRuntime` の `Database` で包み、各モジュールの `Tx` がトランザクションのロールを選びます ([ADR 0028](0028-effect-in-application-and-infrastructure.md)、[ADR 0029](0029-module-data-ownership-and-shared-outbox.md)、[Issue #566](https://github.com/yokozi-jp/agent-software-factory/issues/566))。Nx の `@nx/enforce-module-boundaries` に tag で依存の向きを縛らせることは、引き続き使いません (下の「Nx の `@nx/enforce-module-boundaries` と tag」)。repo-policy が tag から役割を読み、役割ごとの規則で package.json の依存の宣言を確かめるのは許します。この検査は、宣言した依存を package の名前の一覧と照らしていたもので、その入力を tag に替えました。足す手順は [モジュールを足す手順](../domain-model/add-module.md) です ([Issue #329](https://github.com/yokozi-jp/agent-software-factory/issues/329))。
- **公開 API**: 各 package の `package.json` の `exports` は `"."` (`src/index.ts`) だけです。`@agent-software-factory/claim/src/...` のような深い import は解決できません。repo-policy が `exports` の形を確かめます。ただし `packages/ui` は `"."` を持たず、部品の入口 (`./components/*` など) を `exports` にします ([ADR 0034](0034-shared-ui-package.md))。`packages/db` は `"./node"`、`"./seed"`、`"./testing"` の 3 つで `"."` を持たず ([ADR 0038](0038-db-package.md)、[ADR 0051](0051-shared-package-entries-by-feature.md))、`packages/shared-kernel` は `"."` と機能ごとの入口です ([ADR 0051](0051-shared-package-entries-by-feature.md))。`domain` が import してよいのは `shared-kernel` の `.` と `./result` の型だけです。
- **モジュールの間の方向**: 依存は「締め → 承認 → 申請」の一方向です。申請は承認と締めを、承認は締めを import しません。`shared-kernel` はどのモジュールも import しません。`apps/api` はどのモジュールの `index.ts` も import できます。
  - **events の package への依存**: 上の方向の例外として、モジュールは、どのモジュールの events の package にも依存できます。events の package は、`zod` と `shared-kernel` 以外の workspace の package に依存できません。モジュール本体どうしの方向は変わりません。repo-policy (`modules.ts` の `eventsPackages` と `modulesDependOneWay`) が止めます。
  - **止める仕組み**: モジュールは、`package.json` の依存に書いたモジュールだけを import できます。pnpm は、各 package の `node_modules` に直接の依存だけを置き、hoist しません ([pnpm の Motivation](https://pnpm.io/motivation) の "Creating a non-flat node_modules directory")。そのため、依存に書いていないモジュールの import は、型だけの import でも TypeScript が解決できず、`vp check` の型検査で失敗します。依存の宣言そのものの向きは、repo-policy (`tools/scripts/src/checks/repo-policy/modules.ts`) が、モジュールの順序 `moduleOrder` (締め、承認、申請) と照らします。各モジュールは、後ろのモジュールと `shared-kernel` にだけ依存でき、`shared-kernel` はどれにも依存できません。
  - **解決の迂回を止める**: tsconfig の `paths` と `baseUrl`、`vite.config.ts` の `alias`、pnpm の `shamefullyHoist`、`nodeLinker: hoisted`、workspace の scope を含む `publicHoistPattern` は、宣言していない package を解決できるようにします。repo-policy がこれらを止めます。ただし、すべての target が自分の `./src/` の下にある `paths` は、[ADR 0033](0033-shadcn-base-ui-tailwind-v4-storybook.md) で許しました。
- **層**: 各モジュールの `src/` を `domain`、`application`、`infrastructure`、`http` に分けます。`domain` は何も import しません (`shared-kernel` の型の `import type` だけを許します)。`application` は `domain` だけを、`infrastructure` と `http` は `application` と `domain` を import し、互いには import しません。モジュールの外から `infrastructure` と `http` の中は、公開 API の規則で import できません。
- **HTTP の部品と Hono の import**: Hono (`hono` と `@hono/*`) を import できるのは、HTTP の部品の `src/http/`、`apps/api/src/app.ts`、入口のファイル `apps/api/src/server.ts`、テスト、`shared-kernel` の `problem` と `idempotency-http` の入口 ([ADR 0051](0051-shared-package-entries-by-feature.md)) だけです ([Issue #553](https://github.com/yokozi-jp/agent-software-factory/issues/553))。`domain`、`application`、`infrastructure`、ドライバの `infrastructure` が Hono に依存すると、業務の規則と DB の実装が HTTP の枠組みに縛られるためです。`apps/web` (`hc`) と `apps/worker` にはかけません。
  - **apps/api の HTTP の部品**: 種類ごとのディレクトリに置きます。`http/route/` は `OpenAPIHono` の sub-app (`health.ts`、`me.ts`。route を足す形は、これを写す)、`http/middleware/` はリクエストの文脈とアクセスログ (`logging.ts`)、CSRF (`csrf.ts`)、session の guard (`session.ts`)、検証の hook (`validationHook`) と sub-app を作る `createRouter()` は、モジュールの `http` 層も使うので `shared-kernel` の `problem` の入口にあります (`http/route/router.ts` はそれを `ApiVariables` で包みます)。`app.ts` は middleware を並べて sub-app を `.route("/", …)` で付けるだけで、`createRoute` を書きません。完全な path を `createRoute` の `path` に書く理由と、`openapi.json` と `hc` の型が変わらない理由は [ADR 0047](0047-api-contract-with-zod-openapi-and-hc.md) です。Better Auth の組み立て (`auth/`) は HTTP の部品ではないので、`src/auth/` に残します。`/api/auth/*` は契約の外 ([ADR 0035](0035-problem-details-for-api-errors.md)) なので `app.ts` に残します。
  - **モジュールの route**: モジュールの route は、`packages/<module>/src/http/route/` に sub-app として置きます。層の名前は `http` のままで、`route/` はその下のディレクトリです (層の import の検査は `http` の中のディレクトリを見ません。repo-policy が見るのは、`route/` にファイルがあるかどうかだけです)。interface と登録は次のとおりです ([Issue #554](https://github.com/yokozi-jp/agent-software-factory/issues/554)、最初の route は申請の `POST /api/claims`)。
    - **公開 API**: モジュールの `index.ts` が `<module>Router({ runtime })` を export します (`claimRouter`)。完全な path を持つ `OpenAPIHono` の sub-app を返し、`index.ts` が `http` の route と `infrastructure` の実装 (保存先の port の実装) をつなぎます。`http` と `infrastructure` は互いに import しないので、実装は `index.ts` が値で `http` に渡します (`Effect.provideService`。`Layer` を作らず、リクエストごとに `Layer` を作ることもありません)。
    - **起動時に渡すもの**: `runtime` (`shared-kernel/tenant-db` の `DatabaseRuntime`) だけです。モジュールの DB は渡しません。use case が runtime の `Database` と自分の `Tx` から得ます ([ADR 0028](0028-effect-in-application-and-infrastructure.md)、[ADR 0029](0029-module-data-ownership-and-shared-outbox.md))。ロガーは渡しません。アクセスログと 5xx のログは `app.ts` の middleware が書きます ([ADR 0049](0049-logging-with-pino-behind-a-logger-interface.md))。モジュールの `http` 層がログを書く必要が出たときに足します。
    - **リクエストごとに読むもの**: テナントと操作する人、リクエストの ID は `RequestContext` (`shared-kernel` の `.`)、冪等キーは `requireIdempotencyKey` の `c.var.idempotencyKey` ([ADR 0040](0040-idempotency-key-in-module-schema.md))、現在時刻は `currentInstant` で、route の handler が 1 回読み、use case に引数で渡します。`apps/api` の `requestContextFromSession` (`/api/*` の全部)が、セッションの active organization と利用者から文脈を作り、テナントを使う route が `requireRequestContext` (`shared-kernel` の `problem`) で受けます。文脈がなければ、セッションがないとき 401、active organization がないとき 403 (`/problems/no-tenant`) です。テナントは、クライアントが送る値を使いません ([ADR 0011](0011-tenant-id-and-rls-from-the-start.md)、[ADR 0022](0022-better-auth-cookie-bff.md))。
    - **許可の証 (`Permit`)**: 起動時にもリクエストの入力にも入りません。application の `authorize` が作り、domain の遷移の関数に渡します ([ADR 0045](0045-authorization-policy-in-application-with-permit-token.md))。http 層は `actor` を use case に渡すだけです。型 `Permit` は `shared-kernel` の `.` にあります。
    - **application が `Tx` を持たない形**: `application` は `infrastructure` を import できないので、トランザクションの tag (`ClaimTx`) を名指せません。保存は application の port (`ClaimStore`) の 1 つのメソッドにし、infrastructure の実装が `inTenantTransaction` と `withIdempotencyKey` を呼びます。応答の本文は application が `respond` で作り、実装は鍵が新しいときだけ呼びます。
    - **`apps/api` への登録**: `app.ts` に、モジュールごとに `.route("/", claimRouter({ runtime }))` を 1 行ずつ連鎖させます。Hono の `AppType` は、メソッドをつなげた型からしか作られないためです ([Hono の RPC のガイド](https://hono.dev/docs/guides/rpc))。配列に並べてループで付ける形にすると、型が消えます。
  - **止める仕組み**: 禁止の表 (`lint-restrictions.json`) の `hono` の欄です。`vite.config.ts` の `honoPattern` を、`packages/*/src/**` (`http` と `domain` を除く各層。`domain` は外部ライブラリをすべて止める)、ドライバの `infrastructure`、`apps/api/src/**` にかけます。`http` の層と `apps/api/src/http/**`、`app.ts` の override はこれを持たず、`server.ts` とテストの override も持ちません。fixture は、止める行を `apps/api/src/__fixtures__/hono.ts`、`packages/module-fixtures/src/` の直下と `application`、`infrastructure`、ドライバの `infrastructure` に、通す行を `apps/api/src/http/__fixtures__/hono.ts`、`packages/module-fixtures/src/http`、`apps/api/src/__fixtures__/hono.test.ts` に置きます。
- **モジュールの中の循環**: ルートの `vite.config.ts` が、Oxlint の `import/no-cycle` を `packages/*/src`、`packages/*/events/src`、`apps/*/src` にかけます。2 つ以上のファイルが互いに import する循環を止めます。この規則は他の規則を設定しない 1 つの override にして、他の override の規則を消しません。Oxlint 1.89.0 は、ルートの `plugins` に `import` がないと module graph を作らず、override だけでは何も報告しないので、ルートに `plugins` を書いています ([CI](../tooling/ci.md))。fixture は `packages/module-fixtures/src/__fixtures__/cycle-a.ts` と `cycle-b.ts` です。
- **`domain` の書き方の規則**: `domain` の中身の書き方 (純粋な関数、判別可能な union、自作の `Result`) は [ADR 0027](0027-domain-model-as-pure-functions-and-unions.md) で、Effect を使う層 (`application` と `infrastructure` だけ) は [ADR 0028](0028-effect-in-application-and-infrastructure.md) で決めました。`domain` の override には、import の規則に加えて、`Date` の値を止める `no-restricted-globals`、`Math.random` を止める `no-restricted-properties`、`throw` を止める自作の規則 `domain/no-throw` (`tools/lint-plugins/src/domain-plugin.ts`) を足しました ([Issue #259](https://github.com/yokozi-jp/agent-software-factory/issues/259))。型の注釈の `Date` は止まりません。`application` と `infrastructure` の override には、Effect の実行の関数を止める `no-restricted-properties` を足します ([Issue #260](https://github.com/yokozi-jp/agent-software-factory/issues/260))。どちらも、下の「override の組み立て」のとおり、各 override が持つ制限に足します。
- **規則**: ルートの `vite.config.ts` の `layers` (層と、import してよい層) から、`lint.overrides` の `no-restricted-imports` を組み立てます。規則はどのモジュールでも同じなので、モジュール名を使いません。止めるものは次のとおりで、どのメッセージにも直し方とこの ADR のパスを書きます。
  - package 名の後に続く subpath と、`<dir>/src` に入る相対パス (`patterns` の `regex`)。`packages/` と `apps/api/src` のすべてのファイルにかけます。
  - `domain` では、`shared-kernel` の値の import、`.` で始まらない import (ライブラリと Node.js の組み込み)、`shared-kernel` 以外の scope 付きの package。
  - 許していない層への相対パス (`../application/...` など)。
- **override の組み立て**: Oxlint は1つのファイルに同じ規則を設定する override が複数あると、最後のものだけを使います。そのため、各 override (`packages/*/src/**` と、各層の `packages/*/src/<layer>/**`) が、そのファイルにかかる制限を全部持ちます。override はすべてのモジュールに同じに届くので、モジュールごとには作りません。`shared-kernel` には層がないので、`packages/*/src/**` の override だけが届きます。`apps/api/src/**` の override も、[ADR 0007](0007-api-on-node-web-standard-app.md) のランタイムの制限と、深い import の制限を両方持ちます。入口のファイルとテストの override は、ランタイムの制限を外し、深い import の制限だけを残します。
- **`domain` の pattern の順序**: Oxlint 1.89.0 は `patterns` を順に調べ、否定 (`!`) を含む `group` が一致すると、その import の検査をやめます。そのため、`shared-kernel` の値の import を止める pattern を (入口に分けた後は、`deepImports` の否定の `group` が入口の import でも一致するので、`domain` の pattern を `deepImports` より前にも置きます。[ADR 0051](0051-shared-package-entries-by-feature.md))、`["@*/*", "!@agent-software-factory/shared-kernel"]` の `group` より前に置きます。順序を逆にすると、`shared-kernel` の値の import が止まりません (2026-10-26 に確かめました)。Oxlint の `regex` は先読み (`(?!...)`) を使えないので、否定の `group` で書いています。
- **検出力 ([Issue #43](https://github.com/yokozi-jp/agent-software-factory/issues/43))**: override ごとに、その override の `files` が届く場所に fixture を1つ置きます。置き場所は `<dir>/__fixtures__/boundaries.ts` です (`<dir>` は `packages/module-fixtures/src`、`packages/module-fixtures/src/<layer>`、`apps/api/src`)。override はすべてのモジュールに同じに届くので、fixture は 1 つの package にだけ置きます。置き場所の `packages/module-fixtures` は、モジュールと同じ層を持ち、fixture だけを持つ package で、サンプル機能のモジュールではありません。fixture はハーネスのセンサーなので、テンプレートから作るシステムでサンプル機能を消しても残るように、サンプル機能のモジュールから分けました ([Issue #319](https://github.com/yokozi-jp/agent-software-factory/issues/319))。`shared-kernel` には層がなく、`shared-kernel` の中から自分の package 名を import すると解決してしまうので、置き場所にしません。モジュールの間の方向は、`packages/module-fixtures/src/__fixtures__/boundaries.ts` の、依存にない `shared-kernel` の import に付けた `@ts-expect-error` が確かめます。`module-fixtures` はどの package にも依存しないので、同じファイルの深い import の行は lint の規則だけを確かめます。`exports` が `./src/index.ts` だけであることは、fixture ではなく repo-policy が確かめます。上の迂回のどれかで解決できるようになると、使われない `@ts-expect-error` (TS2578) で `vp check` が失敗します。違反の行に `oxlint-disable-next-line no-restricted-imports -- 理由` を付けるので、規則が外れたり、`files` が届かなくなったりすると、使われない disable のコメントで `vp check` が失敗します。入口のファイルとテストの override の fixture は、テストの glob に一致するように `apps/api/src/__fixtures__/boundaries.test.ts` にします。
  - 解決できない import (依存にない package、`exports` にない subpath) は、disable のコメントの上に `@ts-expect-error -- 理由` を書きます。TypeScript は、エラーの行から上に向かって `//` のコメントの行を飛ばして指示を探すので、2つのコメントを重ねられます。
  - `domain` の `throw`、`Date`、`Math.random` の fixture は、`packages/module-fixtures/src/domain/__fixtures__/purity.ts` です。型の注釈の `Date` は disable のコメントを付けずに置き、規則が止めないことを `vp check` で確かめます。`shared-kernel` の `Result` は、`src/__fixtures__/result.ts` が、値を欠いた `Ok` や union にない `_tag` の失敗に `@ts-expect-error` を付けて確かめます。
  - `__fixtures__/` は、jscpd (`.jscpd.json` の `ignore`)、Knip (`knip.jsonc` の `ignoreFiles`)、Nx の `production` の入力 (`nx.json`)、`apps/api` と `apps/web` の Vitest (`exclude`)、coverage (`coverage-policy.json` の `notMeasured`) の対象から外します。文を持つ fixture (`runtime-apis.ts`) は、coverage の下限を割るためです。`index.ts` から import しないので、build の成果物にも入りません。
- **書き忘れ**: repo-policy が、`packages/` の `type:module` の package が `moduleOrder` にあること (`modules.ts`)、`src/` と各層について、いずれかの package の `__fixtures__/` に `oxlint-disable-next-line no-restricted-imports` のある fixture があることを確かめます (`lint-fixtures.ts`)。`domain` には、足した 3 つの規則 (`domain/no-throw`、`no-restricted-globals`、`no-restricted-properties`) の disable のコメントがある fixture も、いずれかの package (`packages/module-fixtures`) の `src/domain/__fixtures__/` に求めます ([ADR 0027](0027-domain-model-as-pure-functions-and-unions.md))。 同じ検査が、ADR 0007 のランタイムの制限の fixture (`runtime-apis.ts`) とテストの fixture (`boundaries.test.ts`) も要求します。
- **Nx の graph は package.json から作る**: `nx.json` の `pluginsConfig["@nx/js"].analyzeSourceFiles` を `false` にします。fixture は依存にない package を意図して import します。Nx 24.0.0 は、package.json から解決できない import を TypeScript の JS API (`readConfigFile` など) で解決しようとします。TypeScript 7.0.2 の `typescript` package はその API を持たない (export は `version` と `versionMajorMinor` だけ) ので、graph の作成が `tsModule.readConfigFile is not a function` で失敗しました。モジュールが import できるのは `package.json` に書いた package だけなので、graph の辺も `package.json` の依存と一致します。pnpm の workspace で `workspace:*` を書くリポジトリでは、ソースの解析を切るのは Nx が案内している設定です ([Disable Graph Links Created from Analyzing Source Files](https://nx.dev/docs/guides/tips-n-tricks/analyze-source-files))。

## 名前の経緯

`packages/shared` は、`packages/shared-kernel` (`@agent-software-factory/shared-kernel`、Nx project 名は `shared-kernel`) に改名しました ([Issue #458](https://github.com/yokozi-jp/agent-software-factory/issues/458))。

- **改名の理由**: `shared` だけでは、複数の利用側が使う `ui`、`db`、`i18n` との違いが読み取れません。モジュールの間で合意して共有する小さなモデルとコードは DDD の Shared Kernel にあたるので、名前をそれに合わせました (用語は [GLOSSARY](../../GLOSSARY.md))。
- **フラットのまま**: `ui`、`db`、`i18n`、`module-fixtures` は `packages/` の直下に置きます。`packages/shared/ui` のような 2 階層にはしません。`vite.config.ts` の `packages/*/src/**`、`pnpm-workspace.yaml`、repo-policy の `packages/([^/]+)/package.json`、knip、Nx、lefthook、CSS の `@source` の相対 path が 1 階層を前提にしていて、直し忘れると規則が静かに外れるためです (ADR 0034 が `ui` にかける深い import の禁止など)。
- **`kernel` だけにしない**: OS のカーネルと読めるためです。

## Nx の標準との違い

- Nx の [Folder Structure](https://nx.dev/docs/kb/folder-structure) は、どちらも必須ではない慣習として、2つの配置を挙げています。すべての project を1つのフォルダ (ふつうは `packages/`) の直下に置く flat な配置は、package manager の workspace の既定の形です。`apps/` と `libs/` に分ける grouped な配置では、アプリを入口と設定と機能の組み立てだけにし、機能を library に置くことを勧めています。ここでは、`pnpm-workspace.yaml` がすでに `packages/*` を持つので flat な配置にし、アプリを薄くする考え方は grouped な配置の節から取りました。数十の project を超えたら、grouped な配置を考えます。
- Nx はさらに、library を種類 (`feature`、`ui`、`data-access`、`util`) ごとに別の project に分け、種類と scope の tag で依存を縛ることを勧めています。ここでは、1つのモジュールを1つの project にし、層は project の中のディレクトリにしました。[Project Size](https://nx.dev/docs/kb/project-size) の「いつも一緒に変わるものは分けない」に当たり、1つの業務の変更はふつう全部の層に及ぶからです (判断)。層を project に分けると、3つのモジュールで12の project になります。
- 避けるアンチパターンは、大きな1つの project に全部を入れ、`nx affected` と `nx graph` を効かなくすることです。

## Considered Options

- **方向も lint (`no-restricted-imports` の `paths`) で止める**: 最初の決定です ([Issue #179](https://github.com/yokozi-jp/agent-software-factory/issues/179))。import の行でエラーの説明が出ます。ただ、許すモジュールがモジュールごとに違うので、override をモジュール × 層ごとに組み立て、その数だけ fixture を置く必要がありました (3 モジュールで 42 ファイル)。方向は package.json の依存の宣言でもすでに止まっていて、同じ保証を 2 つの仕組みで持っていました。[Issue #303](https://github.com/yokozi-jp/agent-software-factory/issues/303) で lint から外しました。

- **モジュールの雛形の generator (Nx の local generator)**: 作りません ([Issue #233](https://github.com/yokozi-jp/agent-software-factory/issues/233))。モジュールを足す回数がこの地図の範囲では 1〜2 回で、generator の依存と保守の費用が見合いません。代わりに、既存のモジュールを手順書に従って写し、写したときの登録の漏れを repo-policy で止めます。次のどれかになったら考え直します: 工場の検証でサンプル機能を何度も作り直すとき、派生プロジェクトが始まるとき、「雛形の残り」の generator の基盤が要るとき。
- **Nx の `@nx/enforce-module-boundaries` と tag**: Nx の標準の方法です。Oxlint 版 (`@nx/oxlint`) は Experimental で、Oxlint の JS plugin の API に依存します ([Nx with Oxlint](https://nx.dev/docs/technologies/oxlint/introduction))。Nx に lint を任せない [ADR 0002](0002-nx-orchestrates-vite-plus.md) との整合も確かめていません。tag は project の単位の規則なので、project の中のディレクトリである層の方向は書けません。 採用するなら、tag のない project は何にも依存できないという Nx の規則に合わせて、`apps/*` と events の package にも tag が要ります。
- **役割を package の名前の一覧で持ち続ける**: 最初の形です。ドライバを足すたびに `modules.ts` の 3 つの一覧(`notModules`、`dependOnNone`、`driversOfModules`)の更新が要り、書き忘れると、その package が規則の外に黙って置かれていました ([Issue #552](https://github.com/yokozi-jp/agent-software-factory/issues/552))。tag に替えて、書き忘れを `packagesHaveOneRole` が止めるようにしました。
- **役割を path や `package.json` の独自の field で表す**: path の階層(`packages/drivers/db` など)は、ディレクトリをフラットにする決定(上の「フラットのまま」)に反します。独自の field は Nx の graph から見えません。Nx が tag の置き場として案内する `nx.tags` なら、後から `nx show projects --projects tag:type:driver` で project を引くこともできます。
- **役割を `type:util` と `type:db` に分ける**: Issue #552 の最初の案です。`util` は Nx では低水準の純粋なコードを指し、`ui` を含められず、ドライバの用語([ADR 0054](0054-drivers-with-domain-and-infrastructure-layers.md)、`GLOSSARY.md`)と食い違います。`db` だけの tag は、名前の一覧を tag の名前に写すだけです。`db` はドライバの 1 つとし、例外(モジュールへ `devDependencies` だけで依存する)は名前で引きます。
- **dependency-cruiser**: import を解決したうえで判定できます。再 export 経由の抜け道のように、文字列の照合では見逃す違反が実際に出たら足します。足すときは mise で版を固定します ([ADR 0009](0009-mise-for-pinned-cli-tools.md))。
- **ast-grep**: 規則を自由に書けますが、`no-restricted-imports` で書けることのために道具と規則の言語が1つ増えます。
- **モジュールの `http` 層を `apps/api` に移す (controller を API の側に置く)**: [Issue #553](https://github.com/yokozi-jp/agent-software-factory/issues/553) で退けました。Hono を import する場所が `apps/api` の 1 か所になる利点はありますが、1 つの業務の変更が `packages/<module>` と `apps/api` の 2 つの package に分かれ、モジュールの公開 API (`index.ts`) が use case、失敗の型、型述語まで広がります (判断)。route を use case と同じ package に置くほうが、一緒に変わるものが分かれません。`http` 層に Hono の import を限る lint で、層の分離は保てます。
- **route を `app.ts` に直接並べる**: Issue #553 の前の形です。route が増えるたびに `app.ts` が大きくなり、モジュールが route を持つときに写す形がありません。
- **モジュールの登録の一覧を `apps/api` に持つ (runtime の `Layer` に各モジュールの実装を足す)**: [Issue #554](https://github.com/yokozi-jp/agent-software-factory/issues/554) で退けました。モジュールを足すたびに runtime を作る関数を直すことになり、足し忘れが実行時まで分かりません。モジュールの実装は、モジュールの `index.ts` が route につなぎます (判断)。
- **`Context` を use case に渡す、`apps/api` の `Session` 型をモジュールが読む**: 退けました。モジュールが `apps/api` に依存する逆向きになり、use case が HTTP の枠組みに縛られます。リクエストの文脈は `shared-kernel` の型にしました。
- **`apps/api` の中のディレクトリに分ける**: 最初の案です。Nx の標準から外れ、ワーカーやバッチの入口 ([ADR 0013](0013-api-on-ecs-and-lambda-web-functions.md)) が同じモジュールを使えず、`exports` で深い import を解決できなくすることもできません。

## Consequences

- モジュールを足すときは、手順を [モジュールを足す手順](../domain-model/add-module.md) に書きました。`packages/<name>/` (`package.json` の `name`、`exports`、`nx.name`、`nx.tags` の `type:module`、`check` と `lint-effect` の script、依存してよいモジュールの `workspace:*`、`tsconfig.json`、`src/index.ts`) と、`moduleOrder` の位置を足します。fixture は要りません。repo-policy (`modules.ts`) が、`package.json` の `name` (scope とディレクトリの名前)、`exports` (`"."` の `./src/index.ts` だけ)、`src/index.ts` があること、`nx.name` (ディレクトリの名前)、`check` の script (`vp check`) と `lint-effect` の script、`moduleOrder` にあること、`type:module` の tag があること、`apps/api` への登録 (依存と、route を持つモジュールの `app.ts` の import)、依存の向きを確かめ、`tsconfig.json` がルートを `extends` することも確かめます。`check` の script がないと、Nx がその package の lint も型の検査も走らせず、規則と fixture が何も言えなくなります。層を足すときは `layers` と、`packages/module-fixtures` に層のディレクトリと fixture を 1 つ足します。忘れると repo-policy が止めます。サンプル機能を消すときも、`packages/module-fixtures` と `packages/shared-kernel` は残します。repo-policy は、この 2 つがどの workspace の package にも依存しないことを確かめます。
- 依存の向きに反する import のエラーは、lint の「modules depend one way」ではなく、TypeScript の「Cannot find module」です。依存を足して解決しようとすると、repo-policy が向きを説明して止めます。説明が出る場所が、import の行から `package.json` を変えるときに移ります。
- 判定は import の文字列の照合だけです。解決した先は見ないので、許されたモジュールを経由した再 export、文字列を組み立てた動的な `import()`、`require` は見逃します。層の規則は、相対パスの `../` の並びの直後の名前だけを見ます。`domain/sub/x.ts` から `../../infrastructure/...` は止まりますが、層のファイルからモジュールの `src/index.ts` への import (`domain/x.ts` の `../index.ts`) は止まりません。`domain/sub/x.ts` の `../index.ts` (`domain/index.ts`) と文字列で見分けられないためです。`index.ts` が層を再 export すると、そこから層の方向を飛び越えられます。層の中に層と同じ名前のディレクトリ (`domain/http/` など) を作ると、そこへの `../http` も止まります。
- 他のモジュールの表を直接読み書きしないこと (DB の表の所有) は、import の検査では見つけられません。[ADR 0029](0029-module-data-ownership-and-shared-outbox.md) が、モジュールごとの DB のロールの権限と、カタログのテストで止めると決めました。
- `packages/*/src` のランタイムの制限 ([ADR 0007](0007-api-on-node-web-standard-app.md)、[Issue #178](https://github.com/yokozi-jp/agent-software-factory/issues/178)) のうち、import の制限は別の override ではなく、`vite.config.ts` の `moduleImports` に足しました。別の override にすると、最後の override だけが使われ、どちらかの制限が消えます。グローバルの制限は `no-restricted-imports` と別の規則なので、ADR 0007 の override が `packages/*/src/**` にも届きます。
- 保証カタログには、「モジュール境界」(方向、package 名での import、層) と「禁止 API」([ADR 0007](0007-api-on-node-web-standard-app.md)) の2行を足します。ゲートはどちらも `vp check` です。カタログはまだなく、作る Issue ([保証カタログを置き、カタログと設定のずれを repo-policy で検出する](https://github.com/yokozi-jp/agent-software-factory/issues/139)) の Implementation Decisions に、作るべき行として2行を足しました。
