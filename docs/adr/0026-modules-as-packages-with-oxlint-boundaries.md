# ADR 0026: モジュールは packages/ の Nx project にし、方向は package.json の依存で、層は Oxlint の no-restricted-imports で止める

サンプル機能 (経費精算) はモジュラーモノリスにし、機能ごとのモジュールに分けます。エージェントが逆向きの import や深い import を書いても、`vp check` (pre-commit と CI) で止まるようにします。道具と配置は [モジュール境界と禁止 API の検査の道具を決める](https://github.com/yokozi-jp/agent-software-factory/issues/145) の解決コメントで決め、[Issue #179](https://github.com/yokozi-jp/agent-software-factory/issues/179) で入れました。モジュールの間の方向を lint から package.json の依存に移し、override と fixture をモジュールごとから層ごとにしたのは [Issue #303](https://github.com/yokozi-jp/agent-software-factory/issues/303) です。

## ルール

- **配置**: モジュールは `packages/` の直下に、1つずつ Nx project (pnpm workspace の package) として置きます。申請は `packages/claim`、承認は `packages/approval`、締めは `packages/closing`、モジュールが共有するコードは `packages/shared` です。モジュールの境界の検出力の fixture は、モジュールの形をした `packages/module-fixtures` に置きます (下の「検出力」)。UI の部品は、モジュールでも `shared` でもない共有 package の `packages/ui` に置きます。これは例外で、`moduleOrder` に入れず、層と `exports` の規則を変えます ([ADR 0034](0034-shared-ui-package.md))。`apps/api` は入口のファイルと、モジュールの route を組み立てる `app.ts` だけを持つ薄い入口にし、モジュールを `workspace:*` の依存として持ちます。
- **公開 API**: 各 package の `package.json` の `exports` は `"."` (`src/index.ts`) だけです。`@agent-software-factory/claim/src/...` のような深い import は解決できません。repo-policy が `exports` の形を確かめます。ただし `packages/ui` は `"."` を持たず、部品の入口 (`./components/*` など) を `exports` にします ([ADR 0034](0034-shared-ui-package.md))。
- **モジュールの間の方向**: 依存は「締め → 承認 → 申請」の一方向です。申請は承認と締めを、承認は締めを import しません。`shared` はどのモジュールも import しません。`apps/api` はどのモジュールの `index.ts` も import できます。
  - **止める仕組み**: モジュールは、`package.json` の依存に書いたモジュールだけを import できます。pnpm は、各 package の `node_modules` に直接の依存だけを置き、hoist しません ([pnpm の Motivation](https://pnpm.io/motivation) の "Creating a non-flat node_modules directory")。そのため、依存に書いていないモジュールの import は、型だけの import でも TypeScript が解決できず、`vp check` の型検査で失敗します。依存の宣言そのものの向きは、repo-policy (`tools/scripts/src/checks/repo-policy/modules.ts`) が、モジュールの順序 `moduleOrder` (締め、承認、申請) と照らします。各モジュールは、後ろのモジュールと `shared` にだけ依存でき、`shared` はどれにも依存できません。
  - **解決の迂回を止める**: tsconfig の `paths` と `baseUrl`、`vite.config.ts` の `alias`、pnpm の `shamefullyHoist`、`nodeLinker: hoisted`、workspace の scope を含む `publicHoistPattern` は、宣言していない package を解決できるようにします。repo-policy がこれらを止めます。ただし、すべての target が自分の `./src/` の下にある `paths` は、[ADR 0033](0033-shadcn-base-ui-tailwind-v4-storybook.md) で許しました。
- **層**: 各モジュールの `src/` を `domain`、`application`、`infrastructure`、`http` に分けます。`domain` は何も import しません (`shared` の型の `import type` だけを許します)。`application` は `domain` だけを、`infrastructure` と `http` は `application` と `domain` を import し、互いには import しません。モジュールの外から `infrastructure` と `http` の中は、公開 API の規則で import できません。
- **`domain` の書き方の規則**: `domain` の中身の書き方 (純粋な関数、判別可能な union、自作の `Result`) は [ADR 0027](0027-domain-model-as-pure-functions-and-unions.md) で、Effect を使う層 (`application` と `infrastructure` だけ) は [ADR 0028](0028-effect-in-application-and-infrastructure.md) で決めました。`domain` の override には、import の規則に加えて、`Date` の値を止める `no-restricted-globals`、`Math.random` を止める `no-restricted-properties`、`throw` を止める自作の規則 `domain/no-throw` (`tools/lint-plugins/src/domain-plugin.ts`) を足しました ([Issue #259](https://github.com/yokozi-jp/agent-software-factory/issues/259))。型の注釈の `Date` は止まりません。`application` と `infrastructure` の override には、Effect の実行の関数を止める `no-restricted-properties` を足します ([Issue #260](https://github.com/yokozi-jp/agent-software-factory/issues/260))。どちらも、下の「override の組み立て」のとおり、各 override が持つ制限に足します。
- **規則**: ルートの `vite.config.ts` の `layers` (層と、import してよい層) から、`lint.overrides` の `no-restricted-imports` を組み立てます。規則はどのモジュールでも同じなので、モジュール名を使いません。止めるものは次のとおりで、どのメッセージにも直し方とこの ADR のパスを書きます。
  - package 名の後に続く subpath と、`<dir>/src` に入る相対パス (`patterns` の `regex`)。`packages/` と `apps/api/src` のすべてのファイルにかけます。
  - `domain` では、`shared` の値の import、`.` で始まらない import (ライブラリと Node.js の組み込み)、`shared` 以外の scope 付きの package。
  - 許していない層への相対パス (`../application/...` など)。
- **override の組み立て**: Oxlint は1つのファイルに同じ規則を設定する override が複数あると、最後のものだけを使います。そのため、各 override (`packages/*/src/**` と、各層の `packages/*/src/<layer>/**`) が、そのファイルにかかる制限を全部持ちます。override はすべてのモジュールに同じに届くので、モジュールごとには作りません。`shared` には層がないので、`packages/*/src/**` の override だけが届きます。`apps/api/src/**` の override も、[ADR 0007](0007-api-on-node-web-standard-app.md) のランタイムの制限と、深い import の制限を両方持ちます。入口のファイルとテストの override は、ランタイムの制限を外し、深い import の制限だけを残します。
- **`domain` の pattern の順序**: Oxlint 1.89.0 は `patterns` を順に調べ、否定 (`!`) を含む `group` が一致すると、その import の検査をやめます。そのため、`shared` の値の import を止める pattern を、`["@*/*", "!@agent-software-factory/shared"]` の `group` より前に置きます。順序を逆にすると、`shared` の値の import が止まりません (2026-10-26 に確かめました)。Oxlint の `regex` は先読み (`(?!...)`) を使えないので、否定の `group` で書いています。
- **検出力 ([Issue #43](https://github.com/yokozi-jp/agent-software-factory/issues/43))**: override ごとに、その override の `files` が届く場所に fixture を1つ置きます。置き場所は `<dir>/__fixtures__/boundaries.ts` です (`<dir>` は `packages/module-fixtures/src`、`packages/module-fixtures/src/<layer>`、`apps/api/src`)。override はすべてのモジュールに同じに届くので、fixture は 1 つの package にだけ置きます。置き場所の `packages/module-fixtures` は、モジュールと同じ層を持ち、fixture だけを持つ package で、サンプル機能のモジュールではありません。fixture はハーネスのセンサーなので、テンプレートから作るシステムでサンプル機能を消しても残るように、サンプル機能のモジュールから分けました ([Issue #319](https://github.com/yokozi-jp/agent-software-factory/issues/319))。`shared` には層がなく、`shared` の中から自分の package 名を import すると解決してしまうので、置き場所にしません。モジュールの間の方向は、`packages/module-fixtures/src/__fixtures__/boundaries.ts` の、依存にない `shared` の import に付けた `@ts-expect-error` が確かめます。`module-fixtures` はどの package にも依存しないので、同じファイルの深い import の行は lint の規則だけを確かめます。`exports` が `./src/index.ts` だけであることは、fixture ではなく repo-policy が確かめます。上の迂回のどれかで解決できるようになると、使われない `@ts-expect-error` (TS2578) で `vp check` が失敗します。違反の行に `oxlint-disable-next-line no-restricted-imports -- 理由` を付けるので、規則が外れたり、`files` が届かなくなったりすると、使われない disable のコメントで `vp check` が失敗します。入口のファイルとテストの override の fixture は、テストの glob に一致するように `apps/api/src/__fixtures__/boundaries.test.ts` にします。
  - 解決できない import (依存にない package、`exports` にない subpath) は、disable のコメントの上に `@ts-expect-error -- 理由` を書きます。TypeScript は、エラーの行から上に向かって `//` のコメントの行を飛ばして指示を探すので、2つのコメントを重ねられます。
  - `domain` の `throw`、`Date`、`Math.random` の fixture は、`packages/module-fixtures/src/domain/__fixtures__/purity.ts` です。型の注釈の `Date` は disable のコメントを付けずに置き、規則が止めないことを `vp check` で確かめます。`shared` の `Result` は、`src/__fixtures__/result.ts` が、値を欠いた `Ok` や union にない `_tag` の失敗に `@ts-expect-error` を付けて確かめます。
  - `__fixtures__/` は、jscpd (`.jscpd.json` の `ignore`)、Knip (`knip.jsonc` の `ignoreFiles`)、Nx の `production` の入力 (`nx.json`)、`apps/api` と `apps/web` の Vitest (`exclude`)、`apps/api` の coverage (`coverage.exclude`) の対象から外します。文を持つ fixture (`runtime-apis.ts`) は、coverage の下限を割るためです。`index.ts` から import しないので、build の成果物にも入りません。
- **書き忘れ**: repo-policy が、`packages/` の `shared` と `module-fixtures` 以外の package が `moduleOrder` にあること (`modules.ts`)、`src/` と各層について、いずれかの package の `__fixtures__/` に `oxlint-disable-next-line no-restricted-imports` のある fixture があることを確かめます (`lint-fixtures.ts`)。`domain` には、足した 3 つの規則 (`domain/no-throw`、`no-restricted-globals`、`no-restricted-properties`) の disable のコメントがある fixture も、いずれかの package (`packages/module-fixtures`) の `src/domain/__fixtures__/` に求めます ([ADR 0027](0027-domain-model-as-pure-functions-and-unions.md))。 同じ検査が、ADR 0007 のランタイムの制限の fixture (`runtime-apis.ts`) とテストの fixture (`boundaries.test.ts`) も要求します。
- **Nx の graph は package.json から作る**: `nx.json` の `pluginsConfig["@nx/js"].analyzeSourceFiles` を `false` にします。fixture は依存にない package を意図して import します。Nx 24.0.0 は、package.json から解決できない import を TypeScript の JS API (`readConfigFile` など) で解決しようとします。TypeScript 7.0.2 の `typescript` package はその API を持たない (export は `version` と `versionMajorMinor` だけ) ので、graph の作成が `tsModule.readConfigFile is not a function` で失敗しました。モジュールが import できるのは `package.json` に書いた package だけなので、graph の辺も `package.json` の依存と一致します。pnpm の workspace で `workspace:*` を書くリポジトリでは、ソースの解析を切るのは Nx が案内している設定です ([Disable Graph Links Created from Analyzing Source Files](https://nx.dev/docs/guides/tips-n-tricks/analyze-source-files))。

## Nx の標準との違い

- Nx の [Folder Structure](https://nx.dev/docs/kb/folder-structure) は、どちらも必須ではない慣習として、2つの配置を挙げています。すべての project を1つのフォルダ (ふつうは `packages/`) の直下に置く flat な配置は、package manager の workspace の既定の形です。`apps/` と `libs/` に分ける grouped な配置では、アプリを入口と設定と機能の組み立てだけにし、機能を library に置くことを勧めています。ここでは、`pnpm-workspace.yaml` がすでに `packages/*` を持つので flat な配置にし、アプリを薄くする考え方は grouped な配置の節から取りました。数十の project を超えたら、grouped な配置を考えます。
- Nx はさらに、library を種類 (`feature`、`ui`、`data-access`、`util`) ごとに別の project に分け、種類と scope の tag で依存を縛ることを勧めています。ここでは、1つのモジュールを1つの project にし、層は project の中のディレクトリにしました。[Project Size](https://nx.dev/docs/kb/project-size) の「いつも一緒に変わるものは分けない」に当たり、1つの業務の変更はふつう全部の層に及ぶからです (判断)。層を project に分けると、3つのモジュールで12の project になります。
- 避けるアンチパターンは、大きな1つの project に全部を入れ、`nx affected` と `nx graph` を効かなくすることです。

## Considered Options

- **方向も lint (`no-restricted-imports` の `paths`) で止める**: 最初の決定です ([Issue #179](https://github.com/yokozi-jp/agent-software-factory/issues/179))。import の行でエラーの説明が出ます。ただ、許すモジュールがモジュールごとに違うので、override をモジュール × 層ごとに組み立て、その数だけ fixture を置く必要がありました (3 モジュールで 42 ファイル)。方向は package.json の依存の宣言でもすでに止まっていて、同じ保証を 2 つの仕組みで持っていました。[Issue #303](https://github.com/yokozi-jp/agent-software-factory/issues/303) で lint から外しました。

- **Nx の `@nx/enforce-module-boundaries` と tag**: Nx の標準の方法です。Oxlint 版 (`@nx/oxlint`) は Experimental で、Oxlint の JS plugin の API に依存します ([Nx with Oxlint](https://nx.dev/docs/technologies/oxlint/introduction))。Nx に lint を任せない [ADR 0002](0002-nx-orchestrates-vite-plus.md) との整合も確かめていません。tag は project の単位の規則なので、project の中のディレクトリである層の方向は書けません。
- **dependency-cruiser**: import を解決したうえで判定できます。再 export 経由の抜け道のように、文字列の照合では見逃す違反が実際に出たら足します。足すときは mise で版を固定します ([ADR 0009](0009-mise-for-pinned-cli-tools.md))。
- **ast-grep**: 規則を自由に書けますが、`no-restricted-imports` で書けることのために道具と規則の言語が1つ増えます。
- **`apps/api` の中のディレクトリに分ける**: 最初の案です。Nx の標準から外れ、ワーカーやバッチの入口 ([ADR 0013](0013-api-on-ecs-and-lambda-web-functions.md)) が同じモジュールを使えず、`exports` で深い import を解決できなくすることもできません。

## Consequences

- モジュールを足すときは、`packages/<name>/` (`package.json` の `name`、`exports`、`nx.name`、`check` と `lint-effect` の script、依存してよいモジュールの `workspace:*`、`tsconfig.json`、`src/index.ts`) と、`moduleOrder` の位置を足します。fixture は要りません。repo-policy (`modules.ts`) が、`package.json` の `name` (scope とディレクトリの名前)、`exports` (`"."` の `./src/index.ts` だけ)、`src/index.ts` があること、`nx.name` (ディレクトリの名前)、`check` の script (`vp check`) と `lint-effect` の script、`moduleOrder` にあること、依存の向きを確かめ、`tsconfig.json` がルートを `extends` することも確かめます。`check` の script がないと、Nx がその package の lint も型の検査も走らせず、規則と fixture が何も言えなくなります。層を足すときは `layers` と、`packages/module-fixtures` に層のディレクトリと fixture を 1 つ足します。忘れると repo-policy が止めます。サンプル機能を消すときも、`packages/module-fixtures` と `packages/shared` は残します。repo-policy は、この 2 つがどの workspace の package にも依存しないことを確かめます。
- 依存の向きに反する import のエラーは、lint の「modules depend one way」ではなく、TypeScript の「Cannot find module」です。依存を足して解決しようとすると、repo-policy が向きを説明して止めます。説明が出る場所が、import の行から `package.json` を変えるときに移ります。
- 判定は import の文字列の照合だけです。解決した先は見ないので、許されたモジュールを経由した再 export、文字列を組み立てた動的な `import()`、`require` は見逃します。層の規則は、相対パスの `../` の並びの直後の名前だけを見ます。`domain/sub/x.ts` から `../../infrastructure/...` は止まりますが、層のファイルからモジュールの `src/index.ts` への import (`domain/x.ts` の `../index.ts`) は止まりません。`domain/sub/x.ts` の `../index.ts` (`domain/index.ts`) と文字列で見分けられないためです。`index.ts` が層を再 export すると、そこから層の方向を飛び越えられます。層の中に層と同じ名前のディレクトリ (`domain/http/` など) を作ると、そこへの `../http` も止まります。
- 他のモジュールの表を直接読み書きしないこと (DB の表の所有) は、import の検査では見つけられません。[ADR 0029](0029-module-data-ownership-and-shared-outbox.md) が、モジュールごとの DB のロールの権限と、カタログのテストで止めると決めました。
- `packages/*/src` のランタイムの制限 ([ADR 0007](0007-api-on-node-web-standard-app.md)、[Issue #178](https://github.com/yokozi-jp/agent-software-factory/issues/178)) のうち、import の制限は別の override ではなく、`vite.config.ts` の `moduleImports` に足しました。別の override にすると、最後の override だけが使われ、どちらかの制限が消えます。グローバルの制限は `no-restricted-imports` と別の規則なので、ADR 0007 の override が `packages/*/src/**` にも届きます。
- 保証カタログには、「モジュール境界」(方向、package 名での import、層) と「禁止 API」([ADR 0007](0007-api-on-node-web-standard-app.md)) の2行を足します。ゲートはどちらも `vp check` です。カタログはまだなく、作る Issue ([保証カタログを置き、カタログと設定のずれを repo-policy で検出する](https://github.com/yokozi-jp/agent-software-factory/issues/139)) の Implementation Decisions に、作るべき行として2行を足しました。

## 出典

- pnpm が各 package の `node_modules` に直接の依存だけを置き、`nodeLinker: hoisted` で npm と同じ平らな構成になること: [pnpm の Motivation](https://pnpm.io/motivation) (2026-10-28 に読んだ)。依存にないモジュールの import を TypeScript が解決しないこと、tsconfig の `paths` を足すと解決して `@ts-expect-error` が使われなくなること: このリポジトリで確かめた (2026-10-28)
- Oxlint の `no-restricted-imports` の `paths`、`patterns` (`group`、`regex`、`allowTypeImports`) と、override の扱い、pattern の順序: Oxlint 1.89.0 (Vite+ 1.4.0) で確かめた (2026-10-26)
- `domain` の override に足した `no-restricted-globals` (`Date`) と `no-restricted-properties` (`Math.random`) が、型の注釈の `Date` を止めないこと: Oxlint 1.89.0 (Vite+ 1.4.0) で確かめた (2026-10-26 と 2026-10-27)。確かめる fixture は `packages/module-fixtures/src/domain/__fixtures__/purity.ts` の `startOf` です。止まる書き方と止まらない書き方の一覧は [ADR 0027](0027-domain-model-as-pure-functions-and-unions.md) の出典にある
- Nx 24.0.0 の `pluginsConfig["@nx/js"]` の既定値: `nx/dist/src/plugins/js/utils/config.js`。graph の作成の失敗と、TypeScript 7.0.2 の `typescript` package の export: このリポジトリで確かめた (2026-10-26)
