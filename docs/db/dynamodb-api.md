# DynamoDB の API 利用

単一・複数レコードの書き込みと一括取得の方針を定める。
結果整合性と強力な整合性の読み込みを使い分ける。
出典は [DynamoDB設計ガイドライン](about.md) (CC BY 4.0) で、OKF の形式に合わせて分割、変更している。

## API利用

主要なAPI操作に関する注意事項・推奨事項をまとめる。

### レコードの書き込み

アイテムの書き込みには、主に`PutItem`と`UpdateItem`の2つのAPIがある。

- `PutItem`: 新規作成または既存アイテムの上書き時に使用する。一部属性だけを変更する用途で使うと、指定しなかった属性は削除される
- `UpdateItem`: 属性を部分的に変更する際に使用する。更新対象のアイテムが存在しない場合、自動的に新規作成(Upsert)される。属性の追加、削除、値の変更、リストやマップ内の要素の操作などが可能。ADDアクションでアトミックなカウンター操作も実現できる。複数の属性の更新や複雑な条件式の設定では、UpdateExpressionの記述が複雑になりがち。アイテム全体を読み込んでから書き戻す「Read-Modify-Write」サイクルをアプリケーション側で実装せずに済み、レイテンシ向上とRCU/WCUの消費を抑えられる

推奨は以下の通り。

- `UpdateItem`で可能な更新処理の場合は、`UpdateItem`の利用を第一に考える
  - インクリメント/デクリメントなどのアトミックカウンターや、既存の属性値に基づいて更新する際は、`GetItem`と`PutItem`を組み合わせた「Read-Modify-Write」サイクルを避ける。競合条件の防止とパフォーマンス向上のため、`UpdateItem`の`ADD`や`SET`アクションを利用する
- `UpdateItem`はアイテムが存在しなかった場合に意図しないレコード作成の懸念があるため、`attribute_exists(PK)`を利用する
- アイテムの新規作成や、既存アイテムを完全に新しいデータで上書きする場合にのみ`PutItem`を利用する
- 大量のデータをバッチで更新する場合は `BatchWriteItem`の利用を検討する

### 複数レコードの書き込み

DynamoDBに複数のレコードを書き込む場合、`PutItem`を繰り返し呼び出す方法と、`BatchWriteItem`を利用する方法がある。`BatchWriteItem`は一度のリクエストで最大25アイテム、かつ合計16MBまで書き込め、NWラウンドトリップ数の削減による性能向上が期待できる。ただし個々の操作に対して`ConditionExpression`（条件付き書き込み）をサポートしないため、アイテムの存在確認や特定の条件を満たす場合のみの書き込みには適さない。

BatchWriteItemを利用する場合、サイズチェックは不要である。DynamoDBの各アイテムは最大400KBのため、1回の`BatchWriteItem`リクエストで送信できる25アイテムの合計サイズは理論上10MB（400KB×25）となる。APIの制限である16MBを常に下回るためである。

> [!WARNING]
> **未処理のアイテムに注意**
>
> `BatchWriteItem` は未処理のアイテム（UnprocessedItems）を返す可能性があるため、リトライロジックを全てのバッチ呼び出しで必ず実装する。

> [!WARNING]
> **WHERE句による一括更新の困難さ**
>
> RDBMSでは、WHERE句で条件に合致する複数のレコードを一括更新することが一般的である。しかしDynamoDBは、プライマリーキーに基づかない条件での一括更新を直接サポートしないため、以下の手順が必要である。
>
> 1. `Scan`または`Query`で更新対象を検索し、そのプライマリーキーや属性を取得
> 2. 検索で得られたプライマリーキーに基づいて、各アイテムに対してUpdate、DeleteItem、BatchWriteItemなどを呼び出す
>
> `BatchWriteItem` のバッチリクエストには `ConditionExpression` を含められない。そのため個々のアイテムの更新に条件付きロジック（例: 「Aという値の場合のみ更新する」）が必要な場合、リトライやエラーハンドリングを加えた上で UpdateItem を繰り返す必要がある。こうしたスクリプトをちょっとしたデータパッチの際にも開発する必要があり、大変である。

<!-- 前の注記と分ける -->

> [!TIP]
> **条件付き書き込み (Conditional Writes)**
>
> DynamoDBの書き込み操作（PutItem, UpdateItem, DeleteItem）には、ConditionExpressionで特定の条件が満たされた場合にのみ操作し、データ一貫性を保つ仕組みがある。主なユースケースは以下の通り。
>
> - 楽観ロック: バージョン番号などの属性を`ConditionExpression`でチェックする
> - 新規作成の排他制御: アイテムが存在しない場合のみ`PutItem`を実行し、不正な上書きを防ぐ（例: `attribute_not_exists(PK)`）
> - 特定のビジネスロジックに基づく書き込み制御
>   - 在庫数が0より大きい場合のみ`UpdateItem`で在庫を減らす
>   - 特定のステータス（例: 承認待ち）の場合のみ、ステータスを「承認済み」に更新する

### 複数レコードの一括取得

プライマリーキーを指定できる場合は、`BatchGetItem`を利用して、異なるテーブルを含む最大100アイテムを、単一のリクエストで効率的に取得できる。ただし、トランザクションは保証しない。パーティションキーが指定できる場合は、`Query`も利用できる。

推奨は以下の通り。

- Queryとフィルターの組み合わせによる検索と、プライマリーキー完全指定のBatchGetItemを選択できる場合は、よりRCUが抑えられるBatchGetItemを利用する

> [!WARNING]
> **Scanは原則、利用しない**
>
> Scan操作は、テーブルまたはセカンダリインデックスの全アイテムを読み込むため、非常にコストが高い。FilterExpressionを指定しても、Scan操作後にフィルターされるためRCUを消費する。Queryに置き換えられないかデータモデルを再検討する。許容するのは、テーブルエクスポートなどの運用目的か、テーブルサイズが小さい場合のみとする。利用する場合はQuery同様、プロジェクション式を設定する。

<!-- 前の注記と分ける -->

> [!WARNING]
> **ページングによる取得漏れに注意する**
>
> Query、Scanは、一度に返せる結果が1MBまでという制約がある。超過した場合は LastEvaluatedKey を使い、クライアント側でページング処理を行う必要がある。これを怠ると、データの取りこぼしがあり得るため注意する。

<!-- 前の注記と分ける -->

> [!TIP]
> **プロジェクション式を活用し応答に含める属性を明示的に指定する**
>
> `Query`を用いる場合は、プロジェクション式 （`ProjectionExpression`）を使用して、必ず応答に含める属性を明示的に指定する。不要な属性の読み込みを回避し、性能向上が期待できる。ただし、RCUは返されるデータ量ではなく、アイテムサイズに基づき計算されるためRCU削減効果はない（[AWS CLIのリファレンス](https://docs.aws.amazon.com/cli/latest/reference/dynamodb/query.html#description)より）。

<!-- 前の注記と分ける -->

> [!TIP]
> **ソート順の指定が可能**
>
> データの取得順序は、ソートキーに対してScanIndexForwardパラメータ（デフォルトはtrueで昇順、falseで降順）で指定できる。

### 結果整合性・強力な整合性の読み込み (Consistent Reads)

DynamoDBは、デフォルトで「結果整合性読み込み（Eventually Consistent Reads）」であるため、書き込み後すぐに読み込むと変更が反映されていない場合がある。「強力な整合性読み込み（Strongly Consistent Reads）」の指定もできるが、レイテンシとRCUが増加する。

推奨は以下の通り。

- 性能・費用の観点から、「結果整合性読み込み」を第一に利用する
- 書き込み直後にその書き込み内容を確実に読み込む必要がある場合（Write-then-Readパターンなど）は、「強力な整合性読み込み」を利用する
  - 例: 在庫を更新した直後に最新の在庫数を表示する場合など、データの即時性がビジネス上のクリティカルな要件となるシナリオ
  - ただし、「結果整合性読み込み」と比較してRCUを倍消費するため、最小限の利用に留める
