# バッチのリリース

バッチは段階的リリースができずインプレースデプロイのみとなるため、切り戻しとバックアップを備える。
依存するジョブは後方互換を保ちながら下流から順にリリースする。
出典は [バッチ設計ガイドライン](about.md) (CC BY 4.0) で、OKF の形式に合わせて分割、変更している。

## リリース

バッチ処理では、B/Gデプロイやカナリアリリースのような段階的なリリースはできない。そのため、インプレースデプロイ（一括で資材を置き換える）のみとなる。

推奨は以下。

- リリース周りのプロセスは、[ADR 0010](../adr/0010-trunk-based-development.md) (トランクベース開発) と [リリース](../repository/release.md) に従って整備する（開発環境、検証環境で動作確認を取ってから、本番環境にデプロイするなど）
- いざというときのために、前回のバージョンへ切り戻せるようにしておく
- もし、影響範囲が広い重要なジョブを大きく改修した場合は、データバックアップを取っておくと良い

### ワークフローで依存関係があるジョブのデプロイ

例えば、A1⇛B1⇛C1 というワークフローで定期的（サイクル的）に実行されるジョブがあるとする。機能改修によりA2、B2、C2に更新したい。ただし、A\~Cで利用するワークテーブルの列名変更があるため、同期を取ってリリースする必要がある。この場合、ナイーブにA、B、Cの順番でデプロイすると、A2の実行結果をB1が処理できずエラーで落ちてしまう。同様にB2の実行結果もC1が処理できずエラーで落ちてしまう。

最も簡易的なリリース方式は、ワークフローを停止して静止点を確保してデプロイすることである。メンテナンスウィンドウを週に数時間程度確保して行うことが多い。しかし、リリース頻度によっては無停止が求められる場合もある。また、データ層を意識したリリース手順は作業者の負荷が大きく、作業ミスを誘発しやすい。

このような場合は、以下のルールを守って改修してもらうと良い。

- 後方互換性があるように改修する。例えば、A1⇛B2 や、B1⇛C2がエラーとならないようにする
  - リリースは、C、B、Aの順番で行う（下流から行う）
  - そのため、例えばB2はA1という古いバージョンのデータを処理できる必要がある
- ERD変更で言えば、列名の削除は行わず、追加のみを許容する
- もし、列を削除する場合は、A2、B2、C2のリリースが終わった、その次のリリースでデータ移行+ERD変更する

もし、B・Cが従来バージョンと全く互換性がない場合は、新しいワークフローバージョンとしてD、Eを追加して切り替える方法も考えられる。しかし、ワークフロー自体が追加となり、リリース手順が複雑かつリハなどのコストも高いことから、なるべく避けるように改修してもらうと良い。

```txt
A1
   ＼ B1 ⇛ C1（★有効）
   ＼ D1 ⇛ E1（無効）

--- リリースタイミングで切り替え ---

A1
   ＼ B1 ⇛ C1（無効）
   ＼ D1 ⇛ E1（★有効）
```
