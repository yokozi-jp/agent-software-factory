# 定時起動ジョブ

定時起動ジョブは、可能なら業務時間帯に起動し、門限とリカバリ用のバッファでバランスを取る。
処理対象が0件の場合の挙動を定義し、起動時間が集中しないよう微妙にずらす。
出典は [バッチ設計ガイドライン](about.md) (CC BY 4.0) で、OKF の形式に合わせて分割、変更している。

## 定時起動ジョブ

定時起動ジョブとは、1日1回、週に1回、月に1回など定められた日時で起動するジョブである。

推奨は以下。

- 起動時間は、可能であれば業務時間帯に設定すると、運用性が高い
  - あくまで可能であればだが、いつでも実行して良いジョブを、ユーザーが少ないとはいえ夜間帯に実行すると、システム運用が大変である
  - 業務のクリティカル度にもよるが、実行時間の自由度が高い場合、通常の業務時間帯（9-17時など）に起動させたほうが、何かあったときのリカバリ体制を取りやすく、運用者フレンドリーである（※通常、夜間帯は頭が働かないため）
- 起動時間は、バッチウィンドウとリカバリ用のバッファでバランスを取る
  - 例えば、10分程度で終わるジョブを17時までに実行させなければならない場合、16:45起動にすると異常終了した際のリカバリは不可能になる。そのため、門限を遵守する場合は、最低でも16:30、できれば16時に起動しておきたい
  - 業務調整が難しい場合は、16時起動のジョブ（大部分のデータを処理）と、16:45起動ジョブ（16時以降に蓄積したデータを処理）の2つに分割できないか検討する
- 月次に1回など周期が大きい場合は、週次など間隔を狭めてアプリケーション側で空振りさせて、動作確認しやすくする
  - ジョブが正しく起動するかの確認に便利である
  - ワークフローエンジン上でスキップ判定をすると、テスト性が良くないためアプリケーション側でスキップすることを推奨する
- 処理対象がゼロ件の場合の挙動を定義する
  - スキップで良い場合、INFOログでその旨を出力する。結合テスト時などに出力先のDBテーブルへの書き込みがゼロ件だと、調査したくなることは意外と多いため、切り分け可能な材料を提供すると良い
  - ゼロ件がありえない場合は、エラーログ出力＋通知を出す
- 同一時間帯に起動時間が集中しないように、微妙にずらす
  - 定時起動ジョブの起動時間が集中しすぎると、DB負荷高騰などが考えられる。そのため、システムタイムチャート（※後述）で各ジョブの起動時間・実行時間・バッチウィンドウを確認し、集中しないようにする
  - 例えば数分程度、起動時間をずらすのもありである
