# 認可の書き方

業務の規則は `domain`、誰が要求したかは `application` の方針の関数 `authorize` で確かめ、許可の証を `domain` の遷移の関数に渡します。理由と採らなかった案は [ADR 0045](../adr/0045-authorization-policy-in-application-with-permit-token.md) にあります。

## 線引き

| 確かめること                                                   | 置き場所                                        |
| -------------------------------------------------------------- | ----------------------------------------------- |
| その審査の上長か、職務分掌（本人は承認も確認もできない）、状態 | `domain` の遷移の関数                           |
| 申請者本人か、経理の役割か、見えるか                           | `application` の `authorize(actor, 操作, 対象)` |

- 基準は「身元、役割、クレームに依る確認は `application`、業務の実体、値、状態遷移の規則は `domain`」です。
- `actor` は、現在時刻と同じく引数で渡します。`Layer` にリクエストごとの状態を持たせません ([application の Effect の書き方](application-effect.md))。
- RLS はテナントだけを分けます。利用者ごとのポリシーを足しません ([ADR 0011](../adr/0011-tenant-id-and-rls-from-the-start.md))。
- 認可のライブラリと方針エンジンを入れません。

## 許可の証

- `authorize` は、許可なら `Permit<操作>` (`__brand` の型) を、拒否なら拒否の `_tag` を返します。
- `domain` の遷移の関数は、操作する人ではなく証を必須の引数に取ります (例: `confirm({ review, permit, now })`)。遷移の関数は、誰が要求したかを知りません。
- 証は `authorize` でだけ作ります。`as` で作りません ([ADR 0020](../adr/0020-typescript-strictness.md))。証の型は、`domain` が `import type` できる場所に置きます。型の書き方は [型の書き方](types.md) です。

## 網羅のテスト

- 方針の関数の単体テストと、遷移の関数の単体テストの 2 つを書きます。
- 操作する人は 7 種類です。申請者本人、同じテナントの別の社員、その審査の上長、別の審査の上長、経理、経理でもあるその審査の上長、経理でもある申請者本人。別のテナントは RLS のテストで確かめます。
- 期待の表はテストの側に 1 つ書き、両方のテストが読みます。操作の union から `satisfies Record<操作, …>` にして、足し忘れを型で止めます。本番の方針の表からは作りません。

## HTTP の応答

| 失敗                                                | 応答 |
| --------------------------------------------------- | ---- |
| 見えない (存在しない、または表で見られない)         | 404  |
| 見えるが、その操作が許されない                      | 403  |
| 状態が合わない、楽観排他の衝突                      | 409  |
| 業務のルールを満たさない (上限、期限、上長がいない) | 422  |
| 人事システムが応答しない                            | 503  |

ステータスコード全体の規約は [Web API の HTTP ステータスコード](../web-api/status-codes.md) です。
パスに id を持つ操作で他人のリソースが 404 になることは、`apps/api` の結合テストが OpenAPI の spec から確かめます。
