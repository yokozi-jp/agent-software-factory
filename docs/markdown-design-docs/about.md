# Markdown設計ドキュメント規約の出典と適用範囲

`docs/markdown-design-docs/` の文書は、フューチャー株式会社の [Markdown設計ドキュメント規約](https://future-architect.github.io/arch-guidelines/documents/forMarkdown/) を元にしている。
対象はアプリケーションの種別ごとの設計ドキュメントで、Markdown でそれらを記載し Git で管理することを前提にする。

### 原文からの変更点

- 1つの文書を、責務ごとに複数の文書に分けた。
- 各文書に OKF の frontmatter と、冒頭の要約を足した。
- VitePress の記法 (`<page-title/>`、`::: tip` などのコンテナ) を、GitHub の Markdown の記法 (`> [!TIP]` など) に置き換えた。
- 原文の章へのリンクを、分割後の文書へのリンクにした。このリポジトリに取り込んだ他のガイドラインへのリンクは、その docs/ の文書へのリンクにした。取り込んでいないガイドライン (AWS、Terraform、データマネジメント、Git ブランチフロー) へのリンクは、原文のサイトの URL にした。
- 原文の `sample/` 配下 (UI 設計書の記入例、`openapi.yaml`、`erd.a5er`、`api_reference.md`、`erd_reference.md`) は、規約ではなく記入例なので取り込まず、本文からのリンクを原文 (GitHub) へのリンクにした。
- I/F 設計書のサンプル (`interface-definition.md`) の、CSV ファイルのレイアウト規格の参照を、JSON を定義する RFC 8259 から CSV を定義する RFC 4180 に直した。RFC 4180、RFC 8259。

## 適用範囲と前提条件

- **対象スコープ**
  - アプリケーションの種別ごとに、設計ドキュメントへ記載すべき内容と、それをどのような Markdown の構造で記載するかが対象
  - 設計ドキュメントを Markdown ベースにし、Git でバージョン管理・レビュー・CI/CD を行うことを前提にする
- **前提条件** (原文の前提)
  - チーム/プロジェクトが 3 ～ 10 名程度の規模
  - Git (GitHub、GitLab) で管理され、コードと設計書が同一リポジトリで管理される
  - システム開発で必要なアプリケーション開発

## 位置づけ

原文の「はじめに」と「本ガイドラインで紹介する設計ドキュメントの位置付け」から、規約として意味のある内容を原文のまま残す。

設計ドキュメントは様々な前提条件 / 制約 / 経緯で作成され、Excel / Word / パワーポイントなどのファイル形式で作成することが多い。
本ガイドラインはそれらを否定するものではなく、様々な利害関係者の要求に応え洗練され続けた上記の設計ドキュメントのテンプレートには、強く敬意を表する。

一方で、設計ドキュメントを精緻に管理していく優先度より、プロダクト開発の効率とビジネスピードをより重視する場合もある。
本ガイドラインでは、後者のプロダクト開発の効率性を重視し、設計ドキュメントが開発以外の観点から求められない場合において、必要最低限必要だと思われるレベルの記載のサンプルを提供する。

また、設計ドキュメントのファイル形式に制約は無いという前提に立つため、設計ドキュメントの陳腐化を防ぐのに有効だと思われる、テキストベース (Markdown) で Git 管理するという思想を採用する。
本ガイドラインで紹介した各設計ドキュメントの記載内容を参考にしつつ、各開発チームにおいて必要な情報を追加 / 削除して利用するという、テンプレートとしての利用を想定する。
