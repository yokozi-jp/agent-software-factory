# タスクの区切りでの振り返り

タスクの区切りで、エージェントは利用者に頼まれなくても `retro` skill を実行し、このセッションから環境の改善候補を出します。
反映するのは、利用者が選んだ候補だけです。
この規則を置いた理由は [ADR 0015](../adr/0015-retro-at-task-boundary.md) にあります。

## タスクの区切り

タスクの区切りは、利用者にタスクの完了を報告する応答の前です。そのタスクで次のどれかをしていれば、報告の前に振り返ります。

- commit した (Issue のない作業も含む)
- PR を作った。CI の結果を確かめてから報告するので、振り返りは CI の結果が出た後になる
- Issue を閉じようとしている (調査の結果を Issue に書いて閉じるときなど)。閉じる前に振り返る

途中の commit、push、レビューの指摘への対応の後は、作業を続けます。振り返るのは、完了を報告するときの 1 回です。
質問への回答のように、commit も PR も Issue の変更もしなかったやり取りは、そのまま答えて終えます。
タスクの途中で利用者に別のタスクを頼まれたら、頼まれたタスクを進め、その完了を報告するときに、両方のタスクをまとめて振り返ります。

## 実行の仕方

1. `retro` skill を読み込みます。Kiro では skill として読み込めます。skill として読み込めない実行環境 (Claude Code、Codex) では、`.agents/skills/retro/SKILL.md` を読んで、その手順に従います。
2. 完了の報告に続けて、skill の手順のとおり、今のセッションを対象に改善候補を重い順に示し、どれを反映するかを利用者に聞きます。ここで応答を終えます。
3. 利用者が選んだ候補を反映します。元のタスクとは別のブランチで直し、PR のタイトルで振り返りから直したことが分かるようにします (例: `docs: 振り返りから、…`。type は変更に合わせる)。PR を作り、CI の結果を報告したら終わりです。

利用者が振り返りを断ったら、そのタスクは振り返りなしで終えます。

## 反映先の選び方

上から順に検討し、最初に当てはまるものにします。

1. **構造で誤りを書けなくする**: 型、モジュールの境界、雛形、ファイルの置き場所を変えて、誤った書き方そのものができないようにします。
2. **検査にする**: 機械的に判定できる誤り (決まった書き方、禁止の API、import の形、ファイルの置き場所の規則) は、lint の規則、`tools/scripts/` の検査、Git hook、Kiro の hook、CI のどれかで止めます。
3. **docs に書く**: 判断が要るものだけを書きます。レビューで見る規約は `CODING_STANDARDS.md`、手順や規約は `docs/` の該当する領域に書き、`AGENTS.md` にはポインタだけを足します ([AGENTS.md、steering、docs、IWE の役割分担](../knowledge/knowledge-architecture.md))。

skill の手順を直したい候補は、この文書に書くか、upstream に提案します。`.agents/skills/**` は `skills-lock.json` と一致させます ([CI](../tooling/ci.md))。
