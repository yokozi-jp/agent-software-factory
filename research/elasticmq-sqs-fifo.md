# ElasticMQ が SQS の FIFO キューと DLQ をどこまで同じに動かすか、Lambda のワーカーをローカルと CI でどう試すかを調べる

## 問い

[Issue #347](https://github.com/yokozi-jp/agent-software-factory/issues/347) の調査。ローカルと CI で SQS の代わりに使う ElasticMQ（ADR 0013）が、本番の SQS の FIFO キューと DLQ と同じに動くか、同じコードで動くか、テストで再配送、重複、順序の逆転、DLQ 行きを作れるかを、一次資料で調べる。

- 仕様の差の表（SQS の公式ドキュメントと、版を固定した ElasticMQ）。FIFO の重複除去の 5 分の窓と `MessageDeduplicationId`、content-based deduplication、`MessageGroupId` ごとの順序とグループの中の失敗、可視性タイムアウトと `ChangeMessageVisibility`、redrive policy と `maxReceiveCount`、DLQ から元のキューへの redrive、`ReceiveRequestAttemptId`、long polling。
- AWS SDK の endpoint を変えるだけで動くか。差し替えが要る API、引数、属性。
- Lambda のワーカー。本番では Event source mapping（ESM）が SQS を読んで `handler(event)` を呼び、`batchItemFailures` を返す。ローカルと CI に ESM はないので、ElasticMQ を読んで handler を呼ぶ test 用の poller が要るか、どこまで本物に似せるか。標準の方法（`sam local` など）があるか。
- ElasticMQ で再現できない振る舞いと、それを確かめられる場所。

決定は下さず、比較と、決めるべき論点で終える。

調べた日は 2026-10-29。AWS アカウントはまだないので、SQS と Lambda の側は公式ドキュメントを読んだだけで、AWS の上では何も実行していない。ElasticMQ の側は、ソースを読み、手元の Docker と JVM で実際に動かして確かめた。各項目は「確認」（ドキュメント、ソース、手元の実行で確かめた事実）と「判断」（私の解釈）を分けて書く。

## 要約

- 版: ElasticMQ は 1.7.1（2026-04-05、2026-10-29 時点の最新で、これより新しい tag はない）に固定して比べた。SDK は `@aws-sdk/client-sqs` 3.1158.0（JSON protocol）。`endpoint` と仮の認証情報を渡すだけで、Send、Receive、Delete、`ChangeMessageVisibility`、Purge、`StartMessageMoveTask` が動いた。
- 本物と同じに動いた（確認）: 5 分の重複除去（削除した後も効く）、content-based deduplication（本文の SHA-256）、グループごとの順序、先頭が処理中のグループは次を返さない、同じグループを 1 回の Receive でまとめて返す、可視性タイムアウトの期限切れで先頭から再配送、`maxReceiveCount` を超えた受信での DLQ 行き、DLQ の重複除去 ID の付け替え、long polling。再配送、重複、順序の逆転（グループの途中のメッセージが DLQ に行って次が先に進む）、DLQ 行きは、キューの可視性タイムアウトを 1〜2 秒にすれば数秒で作れる。
- 違うところ（確認）: (1) FIFO の DLQ から元のキューへの redrive（`StartMessageMoveTask`）は、1.7.1 では FIFO のキューに対して何も移さず、`COMPLETED`、移した数 0 で終わる（標準キューは動く）。(2) 同じ `ReceiveRequestAttemptId` で再試行すると、同じメッセージは返るが receipt handle が変わり、受信回数が増える。SQS は同じ handle を返すと書いている。(3) `DeduplicationScope` と `FifoThroughputLimit` は無視され、重複除去は常にキュー単位。(4) FIFO の元のキューに標準の DLQ を指定しても作れてしまう（SQS は型が合わないと拒否する）。(5) `SetQueueAttributes` で `ContentBasedDeduplication` と `RedriveAllowPolicy` を変えられない。
- Docker の native イメージ（`softwaremill/elasticmq-native:1.7.1`）は、`ListMessageMoveTasks` を呼ぶとサーバーが落ちる。上流は 2026-10-04 に master で直したが、1.7.1 の後の release はまだない。JVM の jar では落ちない。
- ESM と同じ poller は `sam local` にも公式の例にも見つからなかった。`sam local generate-event sqs receive-message` は標準キューの形の 1 件の event を作るだけで、FIFO の属性（`MessageGroupId` など）を含まない。ESM の応答の扱い（`batchItemFailures` の読み方、成功分の削除、失敗分を放置して可視性タイムアウトを待つ）は短いので、test 用の poller を自作するのは小さい（判断）。ただし ESM の拡縮、backoff、同時実行は再現できない。
- ElasticMQ では確かめられず、検証環境か本物の SQS で確かめるもの: ESM の実際の動き、FIFO の redrive、高スループットモード、IAM と KMS と VPC endpoint、短い polling の取りこぼし、メッセージの保持期間。
- SDK 側の落とし穴（確認）: ADR 0013 が Lambda の構成で必須にしている `AWS_USE_DUALSTACK_ENDPOINT=true` は、`endpoint` を上書きした SDK で `Dualstack and custom endpoint are not supported` になる。ローカルと CI でこの環境変数を渡してはいけない。

## 同じコードで動くか

### endpoint を変えるだけで動くところ

- 確認: `new SQSClient({ region: "ap-northeast-1", endpoint: "http://localhost:9324", credentials: { accessKeyId: "x", secretAccessKey: "x" } })` だけで、`SendMessage`、`ReceiveMessage`、`DeleteMessage`、`ChangeMessageVisibility`、`GetQueueAttributes`、`PurgeQueue`、`StartMessageMoveTask`、`ListMessageMoveTasks`（JVM の jar）が動いた。SDK v3 は SQS を JSON protocol で呼び、ElasticMQ は JSON protocol に対応している（Issue [#815](https://github.com/softwaremill/elasticmq/issues/815)、1.6.16 の release で JSON のエラー応答に `X-Amzn-Query-Error` を足した）。
- 確認: 本文の MD5 は、SDK が応答の `MD5OfMessageBody` を検査しても通った。
- 確認: `GetQueueUrl` で URL を取るコードはそのまま動く。URL を `https://sqs.<region>...` の形で組み立てるコードと、ARN の region や account を見るコードは動かない。

## Lambda のワーカー: ESM の代わりの poller

### 本番の ESM がすること（公式の記述）

- 1 回の invoke に batch の Records を渡す。FIFO のキューは `BatchSize` の最大が 10 で、`MaximumBatchingWindowInSeconds` は使えない（[SQS ESM のパラメーター](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-parameters.html)）。
- 成功したら batch のメッセージを削除する。受け取った間は、キューの可視性タイムアウトの間だけ見えなくなる。関数のタイムアウトはキューの可視性タイムアウト以下にする必要があり、AWS は可視性タイムアウトを関数のタイムアウトの 6 倍以上にするよう勧める（[Configuring an SQS event source](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-configure.html)）。
- `ReportBatchItemFailures` を有効にすると、`batchItemFailures: [{ itemIdentifier: messageId }]` の分だけを見えるようにする（成功分は削除される）。FIFO では「最初の失敗で処理を止め、失敗したものと処理していないものをすべて返す」と書かれている。空か null の `batchItemFailures` は全部成功。関数が例外を投げる、応答が不正、`itemIdentifier` が空か存在しない ID の場合は、batch 全体の失敗（[Handling errors for an SQS event source](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-errorhandling.html)）。
- FIFO の batch には複数のグループが入りうる（[FIFO queue delivery logic](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-understanding-logic.html)）。Powertools for AWS Lambda（TypeScript）の `SqsFifoPartialProcessor` は、既定で最初の失敗で止めて残りを失敗にし、`skipGroupOnError` を付けると失敗したグループだけを返して他のグループは続ける（[Batch Processing](https://docs.aws.amazon.com/powertools/typescript/latest/features/batch/)）。
- event の形は、FIFO では `attributes` に `SequenceNumber`、`MessageGroupId`、`MessageDeduplicationId` が加わる（[Using Lambda with Amazon SQS](https://docs.aws.amazon.com/lambda/latest/dg/with-sqs.html)）。

### 標準の方法（`sam local` など）

- `sam local invoke` は 1 回の invoke を手元の container で動かす。`sam local start-lambda` は Lambda の invoke API を手元に立てる。`sam local generate-event` は event の見本を作る（[sam local invoke](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/using-sam-cli-local-invoke.html)、[start-lambda](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/sam-cli-command-reference-sam-local-start-lambda.html)、[generate-event](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/using-sam-cli-local-generate-event.html)）。確認: これらのページに、SQS を polling して関数を呼ぶ ESM の記述はなかった。
- 確認: `sam local generate-event sqs receive-message` の見本（`aws-sam-cli` の `samcli/lib/generated_sample_events/events/sqs/Sqs.json`、commit `7cc2d4e`）は 1 件の Record で、`attributes` は `ApproximateReceiveCount`、`SentTimestamp`、`SenderId`、`ApproximateFirstReceiveTimestamp` だけ。FIFO の `MessageGroupId`、`MessageDeduplicationId`、`SequenceNumber` は含まない。
- 判断: ElasticMQ を読んで handler を呼ぶ公式の例は見つからなかった。「見つからなかった」ことで、存在しないと言い切るものではない。

### 自作の poller に要ること

ElasticMQ の `ReceiveMessage`（`MessageSystemAttributeNames: ["All"]`）は、ESM の event に要る属性（`ApproximateReceiveCount`、`SentTimestamp`、`SenderId`、`ApproximateFirstReceiveTimestamp`、`MessageGroupId`、`MessageDeduplicationId`、`SequenceNumber`）を返す（実行）。そこから `eventSource`、`eventSourceARN`、`awsRegion` を足して Records に整える。

| ESM の振る舞い                                                                                | poller で真似るか                                                | 難しさ（判断）                              |
| --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------- |
| `MaxNumberOfMessages` を `BatchSize`（FIFO は 10 以下）にして Receive、WaitTimeSeconds を使う | 真似る                                                           | 易しい                                      |
| event の形（FIFO の属性を含む Records）                                                       | 真似る                                                           | 易しい                                      |
| 成功したら削除（`DeleteMessageBatch`）                                                        | 真似る                                                           | 易しい                                      |
| `batchItemFailures` にある分は削除せず放置。可視性タイムアウトが切れるのを待つ                | 真似る。`ChangeMessageVisibility` は呼ばない                     | 易しい                                      |
| 例外、不正な応答、存在しない `itemIdentifier` は batch 全体の失敗                             | 真似る                                                           | 易しい                                      |
| `ReportBatchItemFailures` の有無（CDK の設定と同じ値にする）                                  | 設定を共有する                                                   | 易しい。値の持ち方を 1 か所にする必要がある |
| 可視性タイムアウト ≥ 関数のタイムアウト                                                       | CDK の assertion のテストで確かめる（poller では確かめられない） | 別の場所                                    |
| グループごとの並行（ESM は複数のグループを同時に処理する）                                    | 1 つずつ順に処理する poller なら不要。並行を試すなら要る         | 中                                          |
| ESM の拡縮、poller の数、失敗時の backoff、スロットリング                                     | 真似ない                                                         | 再現できない                                |

判断: 1 件の handler の単体の挙動は、poller がなくても、手で作った event を直接渡せば試せる。poller が価値を持つのは、ElasticMQ の再配送と DLQ 行きと組み合わせて、複数回の呼び出しをまたぐ振る舞いを試す時（失敗した batch が次の Receive でどう戻るか、`ApproximateReceiveCount` がどう増えるか）。

確認（ElasticMQ の実行）: グループ A に A1、A2、グループ B に B1 を送ると、1 回の Receive で A1、A2、B1 が順に返る。handler が「最初の失敗で止めて残りを全部 `batchItemFailures` に入れる」と、A1 の失敗で B1 も失敗に数えられる。判断: B1 は自分の失敗でなくても受信回数が増えるので、`maxReceiveCount` が小さいと B1 が DLQ に行きうる。ADR 0013 は「最初に失敗したメッセージで処理を止め、それ以降のメッセージをすべて `batchItemFailures` に入れます」と書いていて、AWS の記述と同じ。複数のグループを 1 つの batch に入れる場合の影響は、ADR に書かれていない。

## テストで作れるもの、作れないもの

| 振る舞い                                                                                                                                                                                                           | ElasticMQ で作れるか      | 作り方、または理由                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 再配送                                                                                                                                                                                                             | 作れる                    | キューの可視性タイムアウトを 1〜2 秒にする。または Receive の `VisibilityTimeout` を指定する。待たずに戻すなら `ChangeMessageVisibility` を `0` にする（新しい receipt handle になる）                                                           |
| 重複                                                                                                                                                                                                               | 作れる                    | 同じ `MessageDeduplicationId` を 2 回送る（キューに 1 件）。または handler が同じメッセージを 2 回受ける（再配送）ことで、受け取る側の重複除去（`processed_message`）を試す                                                                      |
| 順序の逆転（DLQ 経由）                                                                                                                                                                                             | 作れる                    | グループ X に X1、X2、X3 を送り、`maxReceiveCount=2`、可視性タイムアウト 1〜2 秒にして X1 を 2 回受けて削除しない。3 回目の Receive は X1 を DLQ に移して空を返し、4 回目で X2 が返る（実行）。X1 は DLQ に、X2 は元のキューにあり、順序が崩れる |
| 順序の逆転（可視性タイムアウト切れ）                                                                                                                                                                               | 作れる                    | handler が可視性タイムアウトより長くかかると、同じ先頭が別の consumer に返る（同じメッセージを 2 つの consumer が処理しうる）                                                                                                                    |
| DLQ 行き                                                                                                                                                                                                           | 作れる                    | `maxReceiveCount=1` と可視性タイムアウト 1 秒で、約 2〜3 秒。DLQ のメッセージに `DeadLetterQueueSourceArn` が付く                                                                                                                                |
| FIFO の DLQ からの redrive                                                                                                                                                                                         | 作れない（1.7.1）         | FIFO では何も移らない。標準のキューなら動く                                                                                                                                                                                                      |
| 5 分の窓の期限切れ                                                                                                                                                                                                 | 実時間で 5 分待てば作れる | Docker のサーバーには時計を進める手段がない                                                                                                                                                                                                      |
| ESM の拡縮、backoff、同時実行、`ReportBatchItemFailures` の実際の扱い                                                                                                                                              | 作れない                  | ESM がない。poller は応答の扱いだけを真似る                                                                                                                                                                                                      |
| 高スループットモード（`DeduplicationScope`、`FifoThroughputLimit`）                                                                                                                                                | 作れない                  | 無視される                                                                                                                                                                                                                                       |
| 保持期間、短い polling の取りこぼし、in-flight の上限（FIFO は 120,000、[ChangeMessageVisibility の資料](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_ChangeMessageVisibility.html)） | 作れない                  | 実装がないか、挙動が違う                                                                                                                                                                                                                         |
| IAM、KMS、VPC endpoint の到達性                                                                                                                                                                                    | 作れない                  | 検査しない。ADR 0013 の VPC の経路（IPv6、interface endpoint）も確かめられない                                                                                                                                                                   |

## 既存の docs との食い違い

- ADR 0013: 「ローカルと CI では、SQS を ElasticMQ、S3 を S3Mock、メールを Mailpit で代えます」とだけ書き、ElasticMQ が SQS と違う点は書いていない。この調査の違い（FIFO の redrive、`ReceiveRequestAttemptId`、`DeduplicationScope`、DLQ の型、`AWS_USE_DUALSTACK_ENDPOINT` と endpoint の上書き）は ADR に出ていない。「FIFO のキューを読む Event Functions は、最初に失敗したメッセージで処理を止め、それ以降のメッセージをすべて `batchItemFailures` に入れます」は、AWS の記述と合う。ADR は直していない。
- `docs/async/testing.md`: 「Testcontainer などを利用し、モックではなく本物のキューを用いて」と書き、「DLQ への転送もテスト化」を勧める。この調査では、ElasticMQ は本物の SQS ではなく、DLQ 行きは試せるが FIFO の redrive は試せなかった。「本物のキュー」の範囲は、ElasticMQ では足りない部分がある。
- `docs/async/ordering.md` と `docs/async/dlq.md`: 前者は「厳密な順序が要るなら FIFO で DLQ を使わない」、後者は「ポイズンピルは DLQ に転送する前提」で二段構えを勧める。AWS の DLQ の資料（「順序を崩したくなければ FIFO で DLQ を使わない」）は前者と合う。後者は、可用性を優先して順序の崩れを許すという前提を明示している。この前提の違いは、ADR 0013（FIFO と DLQ の併用）がどちらに立つかで決まる。ElasticMQ で順序の逆転が作れることは確認した。
- `docs/async/ordering.md` の「DLQ に移動した時点で、後続のメッセージのロックが解除され」: ElasticMQ では、DLQ に移した Receive が空を返し、次の Receive で後続が返った。SQS で同じ順序で起きるかは、公式の資料に細かい記述がなく、未確認。
- 古いと確かめたもの: `docs/` の記述が一次資料と食い違った点は、見つからなかった。AWS の資料に新しい記述（標準キューでも `MessageGroupId` で fair queues になる）があるが、docs には出ていない。この調査の範囲外。

## 決めるべき論点

1. ローカルと CI の FIFO のテストで、何を表明してよいか。この調査で ElasticMQ と SQS が同じと確かめた範囲（重複、グループの順序、先頭の失敗、DLQ 行き、long polling）に限るか。違うと確かめた範囲（`ReceiveRequestAttemptId`、`DeduplicationScope`、FIFO の redrive、保持期間）は、検証環境か本物の SQS に回すか。
2. test 用の poller を作るか。作るなら、どこまで似せるか（上の表の「真似る」行だけか、グループごとの並行まで）。置き場所と、`BatchSize` と `ReportBatchItemFailures` を CDK と共有する方法。作らず、handler に event を直接渡す単体のテストと、検証環境の E2E に任せる選択もある。
3. FIFO の DLQ の redrive を、運用でどう行うか。`StartMessageMoveTask` に頼るなら、ローカルでは試せない。ElasticMQ の修正を待つ（1.7.1 の後の release はなく、master に未 release の修正がある）か、別の手段にするか。
4. ElasticMQ の版の固定の仕方。tag（`1.7.1`）か digest か。native image か JVM の jar か（native image は `ListMessageMoveTasks` で落ちる）。Renovate での更新の扱い。
5. ローカルと CI のキューの作り方。CDK と同じ属性を使う script か設定か。ElasticMQ が拒否する属性の組み合わせ（`SetQueueAttributes` の `ContentBasedDeduplication` など）を避ける決まり。DLQ の型の一致を CDK のテストで確かめるか。
6. 本番で `DeduplicationScope=messageGroup` と `FifoThroughputLimit=perMessageGroupId` を使うか。使うなら、ElasticMQ のキュー単位の重複除去との違いが、テストの結果を変えうる。判断: 重複除去 ID を Outbox の行の ID のようにグループをまたいで一意にするなら、この違いは出ない。
7. 複数のグループが 1 つの batch に入る時の handler の方針。ADR 0013 の「最初の失敗で止めて残りを全部返す」のままにするか、グループ単位で止めるか（Powertools の `skipGroupOnError`）。前者は、他のグループの受信回数を増やす。
8. ECS の構成で FIFO のキューを読む側（ADR 0013 には Event Functions の読み手だけが書かれている）の扱い。ECS のワーカーが `ReceiveMessage` を自分で呼ぶなら、ElasticMQ でそのまま試せる。`ReceiveRequestAttemptId` を使うかどうかも、ここで決まる。
9. `AWS_USE_DUALSTACK_ENDPOINT=true` の渡し方。Lambda の構成だけで渡し、ローカルと CI では渡さない設定の分け方。
10. 検証環境の smoke に、毒メッセージから DLQ（と redrive）までの経路を入れるか（[使い捨ての検証環境を作り、E2E を流して消す流れ（CD）を決める](https://github.com/yokozi-jp/agent-software-factory/issues/88)）。

## 未確認のこと

- SQS の側の挙動はすべて公式の資料の記述で、AWS の上では実行していない。特に、毒メッセージが DLQ に移るタイミング（受信の時か背景か）と、移った直後に同じグループの次が配送されるまでの時間。
- `maxReceiveCount` の有効な範囲を、SQS の資料で確かめられなかった（ElasticMQ は 1〜1000）。
- 古い receipt handle での削除、`ChangeMessageVisibility` が `MessageNotInflight` になる条件、12 時間を超える変更の結果は、公式の資料の文言だけで、SQS で実行していない。
- ESM が FIFO の batch から、失敗したメッセージと同じグループの後続を、可視性タイムアウトの間どう扱うか（`ChangeMessageVisibility` を呼ぶか）。資料に明記がなく、「呼ばない」は私の推測。
- `sam local` に、ESM に相当する機能が実はないか。ドキュメントのページと `Sqs.json` は読んだが、`aws-sam-cli` のソース全体は読んでいない。
- `ReceiveRequestAttemptId` の期限（5 分）を過ぎた後の SQS の挙動。ElasticMQ は例外を投げる。
- ElasticMQ の `CancelMessageMoveTask`、`SendMessageBatch` の FIFO での順序（`orderIndex`）、永続化（`persistence`）の設定は試していない。
- 実験を native image と JVM の jar の両方では流していない。native image だけで流した項目（重複、グループ、DLQ 行き、`ReceiveRequestAttemptId`、long polling）が jar でも同じかは、確かめていない。jar だけで流した項目と native image の関係も同じ。ソースは同じなので同じ結果のはずだが、未確認。
- ADR 0013 の構成のうち、ESM が VPC の中の Event Functions を呼ぶ経路（IPv6、interface endpoint）。
