# i18n の方式を比べる

## 問い

[Issue #37](https://github.com/yokozi-jp/hono-nx-vite-plus/issues/37)「i18n の方式を比べる」。
i18next、Paraglide JS、FormatJS（react-intl）、Lingui を、次の観点で比べる。

- Unicode MessageFormat 2（MF2）への対応
- 型安全（翻訳キーと引数の型チェック）
- 翻訳キーの欠落（missing）と未使用（unused）の検査
- Hono（API のエラーメッセージ）と React の両方で使えるか
- Vite+ との組み合わせ

このリポジトリの構成は `apps/web`（React 19、TanStack Router 1.170、Vite+ 1.1.0）と `apps/api`（Hono 4.13、`@hono/node-server`、Node.js、Vite+ 1.1.0）。
いずれも入口は Web 標準の `Request`/`Response` で、ADR 0007 によりアプリのコードは Web 標準 API だけで書く。

## 要約

- 4 つとも React で使える。4 つとも「ランタイムのコア」は framework 非依存で、Hono（Node.js のサーバー）でも呼べる。Paraglide と Lingui はコンパイラ方式、i18next と FormatJS はランタイム方式。
- MF2 を runtime で使えるのは、今は i18next だけ（`i18next-mf2` プラグイン、v2.1.1、messageformat 4.1 の上で動く。2026-10-17）。FormatJS・react-intl、Lingui、Paraglide はいずれも ICU MessageFormat 1（MF1）で、公開された MF2 ロードマップはない（二次資料）。
- MF2 の仕様自体は Unicode CLDR-TC の Final Candidate（2025-03、LDML 47/48 で refine）。TC39 の `Intl.MessageFormat` は Stage 1 のまま。つまり MF2 は「仕様は固まったが、ブラウザ標準と周辺ツールの対応はこれから」の段階。
- 型安全は 4 つとも可能だが方式が違う。Paraglide はコンパイルした message 関数がそのまま型になる（既定で type-safe）。Lingui は typed message IDs を opt-in、i18next は `i18next.d.ts` augmentation（+ v25.4 の selector API）、FormatJS は抽出した型を自分で使う形。
- キーの検査は、i18next が `i18next-cli` で最も充実（`status` が missing、`status --unused` が unused、`lint` が hardcoded string と interpolation 引数不一致）。Lingui は CLI の extract が未使用を obsolete と印、ESLint は hardcoded string 中心で unused ルールは無い。FormatJS は CLI extract と eslint-plugin（placeholder 検査）。Paraglide はコンパイル時に型エラーで missing を検出、未使用は bundler の tree-shake で落ちる。
- Vite+ との相性: Vite+ は Vite 互換の設定（`defineConfig`、`plugins`）なので、Vite プラグイン方式のもの（Paraglide の `paraglideVitePlugin`、FormatJS の `@formatjs/unplugin`、Lingui の `@lingui/vite-plugin`）はそのまま `vite.config.ts` に足せる見込み。i18next は Vite プラグインを必須とせず、ビルドは `i18next-cli` の別ステップで回す。いずれも Vite+ 側での検証は未実施（未確認）。
- 判断: このリポジトリは新規・単一コンテキスト・Nx + Vite+ なので、方式選びは「runtime 方式（i18next / FormatJS）」と「compiler 方式（Paraglide / Lingui）」の対立が本筋。最終判断は別の grilling チケットで人が決める。

## i18next

- ランタイムの i18n フレームワーク。コアは framework 非依存で、React（react-i18next）、Node.js、Deno などで使える（出典: <https://www.i18next.com/> 2026-10-23 取得）。
- MF2 は `i18next-mf2` プラグイン（v2.1.1、2026-10-17）で使える。`i18nFormat` プラグインとして i18next のメッセージ処理を「置き換える」。MF2 を入れると i18next 本体の plural 接尾辞キー（`key_one`）・context キー・`{{var}}` interpolation・nesting `$t()`・formatting が効かなくなり、エラーにはならない（代わりにメッセージ構文側で書く）。出典: <https://www.i18next.com/how-to/using-icu-or-mf2.md>（2026-10-23 取得）。
- MF2 のツールも追いついた: i18next 26.5 で MF2 変数の型チェック、`i18next-cli` に MF2 モード（locale ごとの抽出と lint）、`debug: true` で未パースの警告。出典: <https://www.i18next.com/how-to/using-icu-or-mf2.md>。
- 型安全: `i18next.d.ts` で `CustomTypeOptions` に resources を宣言して augmentation する。v25.4 で `enableSelector` が入り、v26 で既定、v27 で旧 string API を deprecate 予定。TypeScript v5 以上が必要。出典: <https://www.i18next.com/overview/typescript.md>（2026-10-23 取得）。
- キー検査: `i18next-cli`（v1.80.0）が静的解析（SWC）で、
  - `status`: コードで使うのに primary 言語の翻訳ファイルに無いキー（missing）を報告し、非 0 で exit。
  - `status --unused`: ファイルにあるがコードで使われないキー（unused）を報告（読み取りのみ、CI 用）。動的キー（`t(\`error.${code}\`)`）は検出できない。
  - `lint`: hardcoded string の検出、interpolation 引数の過不足、plural カテゴリの検査。ICU/MF2 時は ICU/MF2 パーサで引数を読む。
    出典: <https://github.com/i18next/i18next-cli/blob/main/README.md>（2026-10-23 取得）。
- Hono（API）での使い方: コアは framework 非依存なので、`i18next.createInstance()` した instance を Node のサーバーで呼び、エラーメッセージを翻訳できる。Vite プラグインは必須でない（未確認: Hono 公式の統合ドキュメントは本調査では確認していない）。
- 判断: runtime 方式で、MF2 を今すぐ runtime で使える唯一の候補。標準の慣行は「型安全のために `i18next.d.ts` augmentation を使い、キー管理は `i18next-cli` に寄せる」。避けるアンチパターンは、MF2/ICU プラグインを入れたまま `{{var}}` や `key_one` を書き続けること（無言で効かなくなる）。

## Paraglide JS（inlang）

- コンパイラ方式。message を型付き ESM 関数（`m.greeting({ name })`）にコンパイルし、bundler が未使用の翻訳を tree-shake する。「React、TanStack Start、SvelteKit、任意の Vite アプリ向けの compiler-first i18n」と自称。出典: <https://github.com/opral/paraglide-js/blob/main/README.md>（2026-10-23 取得、@inlang/paraglide-js 2.29.1）。
- 型安全: 既定で type-safe。message キーと引数に autocomplete が効き、typo がコンパイルエラーになる。`emitTsDeclarations`（TypeScript 5.6+）でエディタの型を同期。出典: 同 README。
- Vite ネイティブ: `paraglideVitePlugin({ project, outdir, emitTsDeclarations })` を `vite.config.ts` の `plugins` に足すだけ。公式が「Vite ベースのアプリに最適」と明言。出典: 同 README。
- TanStack Router / Start: README に TanStack Start の統合例があり、「TanStack Router が route tree・loader・typed link を持ち、Paraglide は locale 検出・localized URL・message 関数を担う」。TanStack 側が router の commit ごとに Paraglide を e2e テストしている。例: <https://github.com/TanStack/router/tree/main/examples/react/start-i18n-paraglide>。出典: 同 README。
- Hono / Node サーバー: `paraglideMiddleware(request, async () => ...)` が `Request` を受け、AsyncLocalStorage で request ごとに locale を解決し、`getLocale()` と message 関数が正しい locale を返す。Web 標準の `Request`/`Response` 前提なので ADR 0007 と整合（未確認: Hono 用の公式アダプタの有無）。出典: 同 README。
- メッセージ構文と MF2: inlang message format を使い、`plural`/`number`/`datetime`/`relativetime` の declaration formatter と variants で plural・gender・select を表す。ICU MessageFormat **1** の `{d, date}` や `#` に対応する formatter はあるが、ICU **plugin** 経由で ICU MF1 構文も使える。MF2 への対応は README・docs に記載が無い。出典: 同 README、<https://github.com/opral/paraglide-js/blob/main/docs/file-formats.md>（2026-10-23 取得）。
- missing/unused: missing はコンパイル時に型エラーとして出る。unused は bundler の tree-shake で bundle から落ちる（専用の「未使用キー報告」コマンドは本調査では確認していない）。
- 判断: compiler 方式で bundle が小さく、TanStack Router と Vite の相性が公式に担保されている。標準の慣行は「`paraglideVitePlugin` を 1 つ足し、message を `m.*` で呼ぶ」。避けるアンチパターンは、provider/context を自前で組むこと（Paraglide は不要）。MF2 が要件なら今は非対応。

## FormatJS（react-intl）

- ICU MessageFormat 1 のランタイム実装。`intl-messageformat` がコア（framework 非依存）、`react-intl` が React バインディング。出典: <https://github.com/formatjs/formatjs/blob/main/README.md>（2026-10-23 取得）。
- MF2: `intl-messageformat` は ICU MF1。公開された MF2 ロードマップは確認できず（二次資料: locize のまとめで「FormatJS / react-intl は MF1 のみ、公開 MF2 ロードマップ無し」<https://www.locize.com/blog/messageformat-2-i18next> 2026-10-21 更新）。
- 抽出: `@formatjs/cli`（v6.16.35）の `formatjs extract` でソースから message を抽出し、`--id-interpolation-pattern` で ID を生成。出典: <https://github.com/formatjs/formatjs/blob/main/docs/src/docs/getting-started/message-extraction.mdx>（2026-10-23 取得）。
- lint: `eslint-plugin-formatjs` が ICU メッセージのルールを強制。`enforce-placeholders`（message の placeholder に対応する values を literal object で渡す）、`enforce-default-message`、`enforce-description` など。出典: <https://github.com/formatjs/formatjs/blob/main/docs/src/docs/tooling/linter.mdx>（2026-10-23 取得）。
- Vite: `@formatjs/unplugin` が Vite/Webpack/Rollup/esbuild/Rspack/Rsbuild に 1 コードベースで対応。`oxc-parser` + `magic-string` で、Babel も TS transformer も要らずに message の ICU 検証・ID 注入・`description` 削除を行う。出典: <https://github.com/formatjs/formatjs/blob/main/docs/src/docs/tooling/unplugin.mdx>（2026-10-23 取得）。
- Hono / Node: コアの `intl-messageformat` は framework 非依存なので Node で呼べる。react-intl は React 専用。API 側は `intl-messageformat` か `@formatjs/intl` を直接使う形になる（未確認: Hono 固有の統合の有無）。
- 型安全: 抽出した message を型として使うが、i18next の augmentation や Lingui の Register のような「ID を型で縛る」一次ドキュメントは本調査では確認していない（未確認）。
- 判断: runtime 方式で ICU MF1 の実装が堅い。標準の慣行は「`@formatjs/unplugin` でビルド時に ICU 検証し、`eslint-plugin-formatjs` で placeholder を縛る」。避けるアンチパターンは、`id-interpolation-pattern` を extract とバンドラで食い違わせること（`MISSING_TRANSLATION` になる）。

## Lingui

- compile-time macro + CLI 抽出の軽量 i18n。`@lingui/core`（framework 非依存、~2 kB、message パーサを同梱しない）、`@lingui/react` が React バインディング。React、React Native、Vue、Solid、Astro、Svelte、Node.js で使える。出典: <https://lingui.dev/introduction>（2026-10-23 取得、@lingui/core 6.10.1）。
- メッセージ構文: 内部で ICU MessageFormat **1**。カタログは既定で PO、JSON/CSV も可。message ID はソーステキストから生成（明示 ID も可）。MF2 対応は無い（二次資料: locize のまとめで「Lingui は MF1」）。
- ワークフロー: マクロ（`Trans`、`t`）で UI 文言を書く → CLI `extract` でカタログに収集（削除分は obsolete 印） → 翻訳 → `compile` で最適化 JS に。`compile` が構文を検証する。出典: <https://lingui.dev/introduction>。
- 型安全: typed message IDs を opt-in。`@lingui/core` の `Register` interface を module augmentation して `messageIds` を宣言すると、`i18n._()`・`i18n.t()`・`<Trans id>` が既知 ID の union に絞られ、autocomplete と compile-time エラーが効く。未設定なら `id` は `string` のまま。出典: <https://github.com/lingui/js-lingui/blob/main/website/docs/guides/typed-message-ids.md>（2026-10-23 取得）。
- キー検査: CLI の `extract` が未使用を obsolete と印、`compile` が構文検証。ESLint プラグインは hardcoded string とマクロ誤用が中心（`no-unlocalized-strings`、`t-call-in-function`、`no-expression-in-message` など）で、「未使用キー専用ルール」は無い。出典: <https://github.com/lingui/js-lingui/blob/main/website/docs/ref/eslint-plugin.md>（2026-10-23 取得）。
- Vite: `@lingui/vite-plugin` がカタログを import 時にその場でコンパイルするので `lingui compile` ステップが要らない。`lingui({ macroTransform: true })` で Babel/SWC 無しにマクロも変換（`@lingui/native-tools`）。出典: <https://github.com/lingui/js-lingui/blob/main/packages/vite-plugin/README.md>（2026-10-23 取得）。
- Hono / Node: `@lingui/core` は framework 非依存で、ブラウザでも Node サーバーでも同じ挙動と明言。API のエラーメッセージは `i18n._()` で翻訳できる。出典: <https://lingui.dev/introduction>。
- 判断: compiler 方式だが、Paraglide と違い ICU MF1 カタログ（PO）で、翻訳ツールの相性が良い。標準の慣行は「`@lingui/vite-plugin` でその場コンパイルし、typed message IDs を opt-in、ESLint で hardcoded string を縛る」。避けるアンチパターンは、`compile` を回さず生カタログを runtime で解釈しようとすること（Lingui は compile 前提）。

## 未確認のこと

- 4 つとも「Vite+ 1.1.0 の `vite.config.ts` に各 Vite プラグインを足して実際にビルドできるか」は本調査では実行していない。Vite+ は Vite 互換と理解しているが、プラグイン互換は未検証。
- Hono（`apps/api`）側で、各ライブラリを Node サーバーに組み込んでエラーメッセージを locale 別に返す具体的な配線（ミドルウェアでの locale 検出など）は、Paraglide の `paraglideMiddleware` 以外は一次ドキュメントで確認していない。
- FormatJS の「ID を型で縛る」型安全の一次ドキュメントは確認できていない。react-intl の型は抽出物に依存する前提で書いた。
- MF2 の TC39 `Intl.MessageFormat` Stage と各ライブラリの MF2 ロードマップは、locize（i18next の運営会社）のまとめに依存する部分がある。Unicode の仕様ステータス（Final Candidate、2025-03）は一次（Unicode CLDR-TC）だが、FormatJS・Lingui・Paraglide の「MF2 ロードマップ無し」は二次資料。
- 各ライブラリの bundle サイズ比較（Paraglide の benchmark 47 KB vs i18next 205 KB など）は Paraglide 自身の benchmark。第三者の計測は確認していない。
