## 要約

- OIDC: このリポジトリは 2026-10-22 に作られたので、OIDC の token の `sub` は ID 付きの形（`repo:yokozi-jp@256537235/agent-software-factory@1429355565:...`）になる。2026-07-15 より後に作られたリポジトリは、この形が既定。名前だけの `sub` で信頼ポリシーを書くと `AssumeRoleWithWebIdentity` が失敗する。job が environment を参照すると、`sub` はブランチの代わりに `environment:<名前>` になるので、ブランチは environment の deployment branch の規則で絞る。
- CDK の bootstrap のロールは、同じアカウントの principal を信頼する。GitHub の OIDC のロールに要る権限は、`aws-cdk:bootstrap-role` の tag が `deploy`、`lookup`、`file-publishing`、`image-publishing` のロールへの `sts:AssumeRole` だけ。実際にリソースを作る権限は CloudFormation の実行ロール（`cfn-exec-role`）にあり、既定は `AdministratorAccess`。`cdk bootstrap --cloudformation-execution-policies` で絞れる。
- 削除の失敗の元: S3 の bucket は既定で残り、`RemovalPolicy.DESTROY` でも中身があると消えない（`autoDeleteObjects` が要る）。CDK の `DatabaseCluster` の既定は `RemovalPolicy.SNAPSHOT` で、消すとスナップショットが残る。Lambda と Web Functions が自分で作る log group は CloudFormation の外にあり、消えない（Web Functions は `.local` も作る）。CDK のコンテナイメージと zip は bootstrap の ECR と S3 に溜まり、`cdk destroy` では消えない（`cdk gc` で消す）。
- 時間: VPC に入れた Lambda の削除は 5〜40 分（AWS の Prescriptive Guidance）、ENI の削除は最大 45 分（AWS の Knowledge Center）。CloudFront の distribution の作成は 5〜10 分（AWS の発表）。Aurora の作成と削除の時間は文書にない。2026-06 に CloudFormation と CDK の express mode（`cdk deploy --express`、`cdk destroy --express`）が出て、安定を待たずに終わる。AWS は本番の削除には勧めていない。
- 消し忘れ: GitHub Actions の `if: always()` の step は、workflow を cancel しても動く。job の既定の上限は 360 分。AWS Budgets と Cost Anomaly Detection はどちらも数時間から 24 時間遅れるので、1 回の実行の中では止められない。Budgets の action は IAM や SCP の Deny を付け、EC2 と RDS のインスタンスを止めるだけで、リソースを消さない。定期の掃除は aws-nuke（ekristen の fork、v3.68.3）が使える。
- 新しい sign-up（2026-09 発表、段階的に公開中）には project ごとの spend limit があり、上限に届くと project を止める。ただし、日本の住所では Region がシドニー（`ap-southeast-2`）に固定され、東京（ADR 0013）を使うには advanced features を有効にする必要があり、そうすると spend limit は消える。
- アカウント: AWS Organizations と IAM Identity Center は無料。Control Tower 自体も無料だが、AWS Config の記録が作って消すたびに増える。AWS は管理アカウントに workload を置かないよう勧める。判断: 最小は「管理アカウント（請求と Organizations だけ）」と「検証用のアカウント 1 つ」。Control Tower は個人では入れず、SI の案件では顧客の既存の landing zone に合わせる。
- 費用: 判断（見積もり）: 東京で両方の構成を 1 時間動かして消すと、1 回およそ 0.5 ドル。主なものは Aurora（2 ACU なら 0.30 ドル/時）、NAT Gateway（0.067 ドル/時）、ALB（約 0.04 ドル/時）。消し忘れると、ECS の構成だけで月に約 90 ドル（1 日 3 ドル）かかる。
- SES の sandbox: 送れる宛先は、検証済みのアドレスとドメインと mailbox simulator だけ。1 日 200 通、1 秒 1 通。テスト用のドメインを検証すると、そのドメインのどのアドレスにも送れる。東京は SES の受信に対応しているので、そのドメインの MX を SES に向け、受信のルールで S3 に置けば、E2E がメールの中身を読める。ドメインの検証は DNS の伝播に最大 72 時間かかるので、毎回作って消す stack には入れない（判断）。

## GitHub Actions から OIDC で AWS に入る

### 標準の形

- GitHub の OIDC の provider（`https://token.actions.githubusercontent.com`、audience `sts.amazonaws.com`）を IAM に登録し、それを信頼するロールを作り、workflow に `permissions: id-token: write` を付け、`aws-actions/configure-aws-credentials` で token を交換する（[Configuring OpenID Connect in Amazon Web Services](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)）。
- `id-token: write` は OIDC の token を取る権限だけで、リソースを書き換える権限ではない（同）。
- AWS は custom claims に対応していない。条件に使えるのは `sub` と `aud` など、IAM が持つ condition key だけ（同）。
- `aws-actions/configure-aws-credentials` の README の例は v6.3.0。thumbprint の指定は今は要らない（[configure-aws-credentials の README](https://github.com/aws-actions/configure-aws-credentials/blob/main/README.md)）。

### `sub` の形と、このリポジトリの値

- `sub` の既定の形は、job が environment を参照すると `repo:ORG/REPO:environment:NAME`、参照せず `pull_request` で動くと `repo:ORG/REPO:pull_request`、それ以外は `repo:ORG/REPO:ref:refs/heads/BRANCH` か `refs/tags/TAG`（[OpenID Connect reference](https://docs.github.com/en/actions/reference/security/oidc)）。
- 2026-07-15 より後に作ったリポジトリ、opt in したリポジトリ、その日より後に名前を変えたか移したリポジトリでは、`sub` に owner と repository の ID が入る（`repo:OWNER@OWNER-ID/REPO@REPO-ID:...`）。名前が使い回されても同じ `sub` を作れないようにするため（同、[GitHub changelog 2026-04-23](https://github.blog/changelog/2026-04-23-immutable-subject-claims-for-github-actions-oidc-tokens/)）。
- 信頼ポリシーが名前だけの形で、リポジトリが ID 付きの形を出すと、`AssumeRoleWithWebIdentity` は `Not authorized` で失敗する（[configure-aws-credentials の README](https://github.com/aws-actions/configure-aws-credentials/blob/main/README.md)）。
- このリポジトリは 2026-10-22 に作られた（`gh repo view --json createdAt`）。`GET /repos/yokozi-jp/agent-software-factory/actions/oidc/customization/sub` は `use_immutable_subject: true`、`sub_claim_prefix: repo:yokozi-jp@256537235/agent-software-factory@1429355565` を返した（[REST API endpoints for GitHub Actions OIDC](https://docs.github.com/en/rest/actions/oidc)）。
- 判断: テンプレートから作るリポジトリはどれも ID 付きの形になるので、信頼ポリシーの `sub` は、CDK のコードに値を書かず、リポジトリの設定（owner ID と repository ID）から組み立てる。

### 信頼ポリシーの絞り方

- GitHub は、少なくとも 1 つの条件を付けないと、ほかのリポジトリが token を取れてしまうとする（[OpenID Connect reference](https://docs.github.com/en/actions/reference/security/oidc)）。IAM は `token.actions.githubusercontent.com:sub` の条件を勧める（[Configuring OpenID Connect in Amazon Web Services](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)）。
- `Allow` の文で `ForAllValues:` を使わない。claim がないか綴りを間違えると true になる（[configure-aws-credentials の README](https://github.com/aws-actions/configure-aws-credentials/blob/main/README.md)）。
- environment を使うと、`sub` は `environment:<名前>` になり、ブランチは入らない。GitHub は、environment を使うなら、その environment の保護の規則（deploy できるブランチとタグの制限など）を足すよう勧める（[Configuring OpenID Connect in Amazon Web Services](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)）。
- Dependabot の job の token は `event_name` が `dynamic` になる。`event_name` で条件を付けられるなら、使う event だけを許す（同）。
- fork からの pull request では、secrets は渡らず、`GITHUB_TOKEN` は読み取りだけになる。Dependabot の pull request も同じ扱い（[Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)）。`pull_request_target` で PR のコードを動かすと、権限と secrets を渡す脆弱性になる（同）。
- 判断: 検証環境の deploy と destroy をする job は environment（例: `verification`）を参照し、信頼ポリシーの `sub` を `StringEquals` で `repo:yokozi-jp@256537235/agent-software-factory@1429355565:environment:verification` に固定する。environment の deployment branch の規則で `main` と、検証を許すブランチに絞る。`StringLike` の `repo:...:*` は使わない（どのブランチの、どの workflow からでも入れる）。PR ごとに作るなら、`pull_request`（fork でない）の `sub` を別のロールに与える形も考えられるが、environment の方が GitHub の保護の規則を使える。

### CDK の bootstrap のロールとの関係

- `cdk bootstrap` は、CloudFormation の実行ロール（`cdk-<qualifier>-cfn-exec-role-<account>-<region>`）、deploy のロール、file publishing のロール、image publishing のロール、lookup のロールを作る（[Bootstrap your environment](https://docs.aws.amazon.com/cdk/v2/guide/bootstrapping-env.html)）。qualifier の既定は `hnb659fds`（[Customize AWS CDK bootstrapping](https://docs.aws.amazon.com/cdk/v2/guide/bootstrapping-customizing.html)）。
- deploy、file publishing、image publishing、lookup のロールの信頼ポリシーは、同じアカウント（`AWS::AccountId`）の principal に `sts:AssumeRole` と `sts:TagSession` を許す。`--trust` で別のアカウントを足せる。ExternalId 付きの AssumeRole は既定で拒否する（[bootstrap-template.yaml](https://github.com/aws/aws-cdk-cli/blob/main/packages/aws-cdk/lib/api/bootstrap/bootstrap-template.yaml)）。各ロールには `aws-cdk:bootstrap-role` の tag（`deploy`、`lookup`、`file-publishing`、`image-publishing`）が付く（同）。
- CloudFormation の実行ロールは `cloudformation.amazonaws.com` だけを信頼し、既定で `AdministratorAccess` を持つ。`--cloudformation-execution-policies` で別の managed policy にでき、`--trust` を使うときは指定が必須（[Customize AWS CDK bootstrapping](https://docs.aws.amazon.com/cdk/v2/guide/bootstrapping-customizing.html)、[bootstrap-template.yaml](https://github.com/aws/aws-cdk-cli/blob/main/packages/aws-cdk/lib/api/bootstrap/bootstrap-template.yaml)）。permissions boundary も付けられる（同）。
- deploy のロールは、change set の作成と実行、asset の bucket の読み取りなどを持ち、v32（CLI 2.1120.0）から `AWSCloudFormationReadOnlyAccess` を持つ（[Bootstrap your environment](https://docs.aws.amazon.com/cdk/v2/guide/bootstrapping-env.html)）。lookup のロールは `ReadOnlyAccess` で、secret を読む操作は Deny（[bootstrap-template.yaml](https://github.com/aws/aws-cdk-cli/blob/main/packages/aws-cdk/lib/api/bootstrap/bootstrap-template.yaml)）。
- GitHub Actions のロールに要る最小の権限は、tag が `deploy`、`lookup`、`file-publishing`、`image-publishing` のロールへの `sts:AssumeRole`（Docker の asset があれば `ecr:GetAuthorizationToken` も）（[cdk-pipelines-github の GITHUB_ACTION_ROLE_SETUP.md](https://github.com/cdklabs/cdk-pipelines-github/blob/main/GITHUB_ACTION_ROLE_SETUP.md)）。`cdk deploy` と `cdk destroy` は deploy のロールで CloudFormation を呼び、CloudFormation が実行ロールの権限でリソースを作って消す（[Bootstrap your environment](https://docs.aws.amazon.com/cdk/v2/guide/bootstrapping-env.html)）。
- 判断: OIDC のロールは「bootstrap のロールを assume するだけ」にし、実際の権限の上限は実行ロール（`--cloudformation-execution-policies` か permissions boundary）で決める。検証用のアカウントだけで使うなら、実行ロールは既定の `AdministratorAccess` のままでも、被害はそのアカウントに閉じる。これはアカウントを分けることが前提。避けるアンチパターンは、OIDC のロールそのものに `AdministratorAccess` を付けることと、管理アカウントや本番と同じアカウントに検証環境を作ること。
- OIDC の provider、GitHub のロール、`cdk bootstrap` は検証環境より先にあり、作って消す対象にしない（判断）。bootstrap の stack を消すと、作ったリソースも消える。AWS は termination protection を勧める（[Customize AWS CDK bootstrapping](https://docs.aws.amazon.com/cdk/v2/guide/bootstrapping-customizing.html)）。

- CloudFormation と CDK の express mode（2026-06-30 発表）は、リソースの設定が適用された時点で操作を終え、安定の確認（traffic を受けられること、伝播、片付け）を待たない。AWS の社内の計測で最大 4 倍速い。CDK は `cdk deploy --express`。rollback は既定で off（[発表](https://aws.amazon.com/about-aws/whats-new/2026/06/aws-cloudformation-cdk/)、[Deploy AWS CloudFormation stacks faster with express mode](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cloudformation-express-mode.html)）。
- express mode では、完了の後も CloudFront は数分かけて伝播し、Lambda の削除は片付けが続き、ECS のサービスは task が起動中のことがある。custom resource（CDK の `autoDeleteObjects` など）は express mode でも応答を待つ（[Deploy AWS CloudFormation stacks faster with express mode](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cloudformation-express-mode.html)）。
- `cdk destroy --express` もある。CDK の文書は、本番の stack の削除には express mode を勧めない（[cdk destroy](https://docs.aws.amazon.com/cdk/v2/guide/ref-cli-cmd-destroy.html)）。
- 判断: 時間を支配するのは、作るときは CloudFront（5〜10 分）と Aurora（数字なし）、消すときは VPC に入れた Lambda の ENI（5〜45 分）。VPC そのものの作成と削除は、文書に数字はないが、ENI を待つ部分以外は短いと見る（未確認）。作成は、E2E の前にどのみち traffic が通ることを待つ必要があるので、express mode で縮む時間は、待つ場所が CloudFormation から E2E の前の待ちに移るだけになる。削除で express mode を使うと、ENI の片付けが終わる前に完了と報告されるので、続けて同じ名前の環境を作るときや、片付けの確認の前提が崩れる。判断: 検証環境では、deploy は express mode を試す価値があり、destroy は標準のモードにして、終わりを確かめる。

## 消し忘れを防ぐ仕組み

### workflow の中で消す

- `always()` の条件の step は、失敗しても cancel されても動く。GitHub は、失敗すると workflow が止まり得る処理（ソースの取得など）には `always()` を使わず `!cancelled()` を使うよう勧める（[Evaluate expressions in workflows and actions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions)）。
- cancel のとき、server は動いている job と step の `if` を評価し直し、`always()` のものは続ける。cancel される step には SIGINT を送り、7.5 秒後に SIGTERM、さらに 2.5 秒後に kill する。cancel の対象になった job と step は 5 分後に強制終了する（[Workflow cancellation reference](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation)）。
- job の `timeout-minutes` の既定は 360 分。step の `timeout-minutes` の最大も 360 分（[Workflow syntax for GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)）。
- 判断: 作る job と消す job を分け、消す job は `needs` で作る job と E2E の job につなぎ、`if: always()` にする。cancel のときも、消す job は「cancel の対象」にならないので 5 分で切れない。ただし、runner そのものが落ちたとき、`if` の評価の前に workflow が消されたとき、AWS の認証が切れたときは消えないので、workflow の外の掃除が別に要る。`configure-aws-credentials` の `role-duration-seconds` は既定 1 時間で、15 分から 12 時間まで（[configure-aws-credentials の README](https://github.com/aws-actions/configure-aws-credentials/blob/main/README.md)）。消す job は自分で認証し直すので、作る job の session が切れても消せる（判断）。12 時間まで使うには、IAM のロールの最大 session の長さも上げる（未確認: IAM の側の既定は確かめていない）。

### tag と定期の掃除

- AWS の Prescriptive Guidance は、tag で環境を識別することと、リソースの寿命を決めて自動で消すことを、ベストプラクティスとして挙げる（[Automate deletion of AWS CloudFormation stacks and associated resources](https://docs.aws.amazon.com/prescriptive-guidance/latest/patterns/automate-deletion-cloudformation-stacks-associated-resources.html)）。AWS の multi-account の whitepaper も、sandbox のリソースは一時的なものとし、定期的に消す自動の手順を置く形を示す（[Experimental OUs](https://docs.aws.amazon.com/whitepapers/latest/organizing-your-aws-environment/experimental-ous.html)）。
- aws-nuke は、アカウントのリソースを全部消す道具。元の rebuy-de/aws-nuke は 2024-10 に archive され、ekristen/aws-nuke が保守を引き継いだ（MIT、最新は 2026-10-02 の v3.68.3）（[ekristen/aws-nuke](https://github.com/ekristen/aws-nuke)、`gh api repos/rebuy-de/aws-nuke` で `archived: true`）。
- aws-nuke の安全策: 既定は一覧を出すだけで、消すには `--no-dry-run` が要る。アカウントの alias が必須で、alias に `prod` を含むと止まる。設定の blocklist に少なくとも 1 つのアカウント ID が要り、対象のアカウントが blocklist にあると止まる。対象のアカウントは設定に明示する（[aws-nuke の Caution and Warning](https://aws-nuke.ekristen.dev/warning/)）。aws-nuke の作者は、すべてのリソースを扱えているわけではないと書いている（[README](https://github.com/ekristen/aws-nuke/blob/main/README.md)）。
- 判断: 検証用のアカウントを検証環境だけに使うなら、定期の掃除は「アカウントの中の、bootstrap と OIDC のロール以外を全部消す」でよく、tag の TTL を読む仕組みを自分で書かずに aws-nuke の filter で済む。aws-nuke が blocklist にアカウント ID を要求するのは、管理アカウントや本番が別にある前提で、アカウントを分けることと噛み合う。

### AWS Budgets

- 予算の情報は 1 日に最大 3 回更新され、更新の間隔は普通 8〜12 時間（[Managing your costs with AWS Budgets](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html)）。
- 予算の action は、IAM policy か SCP を付けることと、指定した EC2 と RDS のインスタンスを対象にすること（止める）ができる。管理アカウントからは別のアカウントに SCP を付けられるが、別のアカウントの EC2 と RDS は対象にできない（[Configuring budget actions](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-controls.html)）。
- 予算の監視と通知は無料。action を付けた予算は月に 2 つまで無料で、3 つ目から 1 つ 1 日 0.10 ドル（[AWS Budgets pricing](https://aws.amazon.com/aws-cost-management/aws-budgets/pricing/)）。
- 判断: Budgets は、通知と「新しいリソースを作らせない」ブレーキで、動いているリソース（Fargate、NAT Gateway、ALB、Aurora のクラスター）を消さない。更新が 8〜12 時間おきなので、1 回の実行の中の暴走は止められない。消し忘れの検知は、日に一度の掃除の方が早い。Aurora Serverless v2 のインスタンスを Budgets の action で止められるかは未確認。

### Cost Anomaly Detection

- 請求のデータの処理の後、1 日に約 3 回動く。Cost Explorer のデータは最大 24 時間遅れるので、異常の検知は使ってから最大 24 時間かかる。新しい monitor は検知を始めるまで 24 時間、新しいサービスは 10 日分の履歴が要る（[Detecting unusual spend with AWS Cost Anomaly Detection](https://docs.aws.amazon.com/cost-management/latest/userguide/manage-ad.html)）。
- 判断: 使うたびに作って消す環境は、使い始めは履歴がなく、検知の対象になるまで時間がかかる。保険として有効にし、主な仕組みにはしない。

### 新しい sign-up の spend limit

- 2026-09 に、AWS は新しい sign-up の体験を発表した。Google、GitHub、Apple、Amazon の資格情報で登録でき、多くの新規の顧客はクレジットカードが要らず、最大 200 ドルのクレジットが付く。資源は project に分かれ、paid plan では project ごとに月の spend limit を付けられ、上限に届くとその月は project を止める（[New AWS experience helps builders get started and ship faster](https://aws.amazon.com/about-aws/whats-new/2026/09/New-AWS-Builder-Experience/)）。AWS は、この体験を一部の顧客から順に公開していると書いている（[Compare sign-up options](https://docs.aws.amazon.com/accounts/latest/reference/sign-up-for-aws.html)）。
- spend limit の最小は 20 ドルか、AWS の見積もりの大きい方。実際の費用が 50%、75%、90% に届いたときと、10 日以内に届きそうなときに通知する。任意で、約 7 日前に新しいリソースの起動を止め（AWS が管理する SCP）、約 5 日前に idle の EC2、RDS、SageMaker の endpoint を止め、約 4 日前に費用の大きい EC2、RDS、Lambda、Bedrock、SageMaker を止める。上限に届くと project のリソースを全部止め、データは残す。90 日放っておくとデータを消す（[Create a spend limit in AWS Settings](https://docs.aws.amazon.com/accounts/latest/reference/create-spend-limit.html)）。
- 新しい sign-up の project の Region は、住所の国で決まる。日本は Asia Pacific (Sydney)（`ap-southeast-2`）。別の Region が要るなら、advanced の sign-up を使うか、advanced features を有効にする（[AWS Regions for your projects](https://docs.aws.amazon.com/accounts/latest/reference/project-regions.html)）。新しい sign-up では、CloudFront の機能のうち選んだ Region の外にリソースを作るもの（CloudFront の WAF など）は使えない（同）。
- advanced features を有効にすると、spend limit は消え、作れなくなる。代わりに Budgets、Cost Explorer、Cost Anomaly Detection を使う。Region を選べるようになる。元に戻せない（[Activate advanced AWS features](https://docs.aws.amazon.com/accounts/latest/reference/activate-advanced-features.html)）。
- 新しい sign-up では、Organizations と IAM Identity Center は AWS が管理し、SCP と RCP も AWS が管理する。IAM のロールとユーザーは作れるが、使えるのは programmatic なアクセスだけ（[Compare sign-up options](https://docs.aws.amazon.com/accounts/latest/reference/sign-up-for-aws.html)）。CloudFront、Lambda（Lambda@Edge を除く）、ECS、ECR、ELB、VPC、Aurora、RDS、SQS、SES、S3、Step Functions、EventBridge、CloudFormation、IAM、STS、Budgets は、新しい体験の Free Tier のサービスの一覧にある。Control Tower、Organizations、IAM Identity Center は、advanced features がないと使えない一覧にある（[Supported AWS services for Sign up for AWS (new)](https://docs.aws.amazon.com/accounts/latest/reference/supported-services-sign-up-new.html)）。
- ADR 0013 との食い違い: ADR 0013 は東京を前提にする。新しい sign-up の spend limit を使うと、日本の住所ではシドニーになる。東京を使うには advanced features が要り、そのとき spend limit は消える。spend limit と東京は両立しない。
- 判断: spend limit は「止める」までする唯一の仕組みだが、使えるのは新しい sign-up のシドニーだけで、止める対象も EC2、RDS、Lambda、Bedrock、SageMaker に限られる（NAT Gateway、ALB、Fargate を止めるかは文書にない）。テンプレートの検証環境は東京に置き（ADR 0013）、Budgets と Cost Anomaly Detection と日に一度の掃除で守る。シドニーで検証環境を回す案は、DB や通信の遅延の性質が本番（東京）と変わるうえ、ADR 0013 の決め直しになるので採らない。

## アカウントの分け方

- AWS Organizations は無料。member のアカウントが使ったリソースの分だけ払う（[Billing and pricing for AWS Organizations](https://docs.aws.amazon.com/organizations/latest/userguide/pricing.html)）。IAM Identity Center も追加の費用なし（[IAM Identity Center の 2026-02 の発表](https://aws.amazon.com/about-aws/whats-new/2026/02/aws-iam-identity-center-multi-region-aws-account-access-and-application-deployment/)）。
- AWS は、管理アカウントを管理アカウントでしかできない作業だけに使い、リソースは別のアカウントに置くよう勧める。SCP は管理アカウントのユーザーとロールを制限しないため。請求書の内訳も分かりやすくなる（[Best practices for the management account](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_best-practices_mgmt-acct.html)）。2026-07-10 より後に console で作った organization には、member のアカウントの離脱と閉鎖を止める SCP が root に自動で付く（同）。
- AWS の multi-account の whitepaper は、sandbox を builder かチームごとのアカウントにし、予算を付け、社内のネットワークとつながず、リソースを一時的なものとして定期的に消す形を示す。sandbox と development（社内の資産を扱う）は分ける（[Experimental OUs](https://docs.aws.amazon.com/whitepapers/latest/organizing-your-aws-environment/experimental-ous.html)）。
- Free plan のアカウントは、Organizations に入るか Control Tower の landing zone を作ると、自動で paid plan に上がる（[Choosing a plan](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/free-tier-plans.html)）。Free plan は 6 か月か、クレジットを使い切るまでで、期限が来るとアカウントを止める（[AWS Free Tier FAQs](https://aws.amazon.com/free/free-tier-faqs/)）。Organizations に入ると、追加のクレジットを得る活動は無効になる（同）。
- Control Tower 自体の費用はない。ただし、作って消す workload は、そのたびに AWS Config の configuration item（1 件 0.003 ドル、アカウントと Region ごと）を記録し、Config の費用が増える（[AWS Control Tower pricing](https://aws.amazon.com/controltower/pricing/)）。
- 判断（最小の構成）: 管理アカウント 1 つ（請求、Organizations、IAM Identity Center、Budgets、Cost Anomaly Detection。workload は置かない）と、検証用のアカウント 1 つ（OIDC の provider と GitHub のロール、CDK の bootstrap、検証環境）。人は IAM Identity Center で入り、root と IAM ユーザーの access key は使わない。Control Tower は入れない。理由は、OU と SCP を 2 アカウントのために置く手間に比べて得るものが少なく、作って消す環境では Config の費用が増えるため。
- 判断（個人と SI の違い）: 個人で始めるなら、上の 2 アカウントで足りる。アカウントを足すのは本番を置くとき。SI の案件では、顧客がすでに Control Tower か landing zone を持っていることが多いので、検証用のアカウントを顧客の sandbox か test の OU にもらい、テンプレートは「1 つのアカウントに OIDC のロールと bootstrap がある」ことだけを前提にする。テンプレートが Organizations や Control Tower を作る形にはしない。

## SES の sandbox で確かめられる範囲

- 新しいアカウントは Region ごとに SES の sandbox に入る。sandbox では、送れる宛先は検証済みのメールアドレスとドメインと mailbox simulator だけ。24 時間に 200 通、1 秒に 1 通まで（[Request production access](https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html)）。
- 本番のアクセスの申請は、AWS が 96 時間以内に最初の返事をする。sandbox の外でも、From などに使う ID は検証が要る（同）。
- mailbox simulator（`success@simulator.amazonses.com` など）は sandbox でも使え、送信の上限の日数に数えず、評判の指標にも影響しない。請求は普通のメールと同じ。`bounce+label@...` のように label を付けて、bounce を区別して試せる（[Using the mailbox simulator](https://docs.aws.amazon.com/ses/latest/dg/send-an-email-from-console.html)）。
- ドメインを検証すると、そのドメインのアドレスに送れる（[Request production access](https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html) の「verified email addresses and domains」）。検証は DNS のレコードで行い、伝播に最大 72 時間かかる。検証のレコードは Region ごとに違う（[Creating and verifying identities](https://docs.aws.amazon.com/ses/latest/dg/creating-identities.html)）。
- SES の受信は東京（`inbound-smtp.ap-northeast-1.amazonaws.com`）に対応している（[Amazon SES endpoints and quotas](https://docs.aws.amazon.com/general/latest/gr/ses.html)）。受信には、ドメインの検証、MX レコード、受信のルールが使う AWS のリソースへの権限が要る（[Setting up Amazon SES email receiving](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-setting-up.html)）。
- 判断: 検証環境の E2E は、次の 2 段で確かめる。
  - 送ったこと: アプリの宛先を mailbox simulator の `success@`（label でテストを区別する）にし、SES の送信のイベントか、アプリの Outbox の状態で確かめる。中身は読めない。
  - 中身: テスト用のサブドメイン（例: `e2e.<持っているドメイン>`）を SES で検証し、その MX を東京の SES の受信に向け、受信のルールで S3 に置く。E2E は S3 からメールを読み、宛先、件名、本文、リンクを確かめる。ドメインの ID、受信のルール、S3 の bucket は残す stack に置く。ドメインを持っていることが前提で、なければ simulator の段だけにする。
  - ローカルと CI は Mailpit（ADR 0013）で中身まで確かめているので、検証環境で確かめるのは SES を通る経路（IAM の権限、IPv6 のエンドポイント、From のドメイン）に絞れる。

## ADR 0013 との食い違いと、#88 で決めること

- 食い違い: 新しい sign-up の spend limit は、日本の住所ではシドニーでしか使えず、東京（ADR 0013）とは両立しない（「新しい sign-up の spend limit」の節）。ADR 0013 は直さず、#88 で「spend limit は使わない」と書くのが筋（判断）。
- ADR 0013 の Consequences の「最初の検証環境で確かめる」項目（connector を通した IPv6、Web Functions の log、CloudFront を通した streaming、connector を通した Aurora）は、この調査の範囲で新しく分かったことはない。Web Functions の log は `/aws/lambda/web/<名前>` と `.local` の 2 つの log group に届き、消えずに残るので、CDK で先に作る（「作って消すときに失敗しやすい点」の表）。
- #88 で決める候補（判断）: 作る job と消す job の分け方と `if: always()`、environment の名前と保護の規則、OIDC のロールの `sub`、実行ロールの権限（既定のままか絞るか）、express mode を deploy に使うか、日に一度の掃除（aws-nuke）を入れるか、残す stack と作って消す stack の境目（OIDC、bootstrap、SES の ID と受信、Route 53）、ECS と Lambda の構成を 1 回で両方作るか別々に作るか、PR ごとに作るか main だけか。
