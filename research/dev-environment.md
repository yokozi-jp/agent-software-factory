# 開発環境を再現する方式（devcontainer、doctor の検査のスクリプト、skill）を、WSL2、worktree、クラウドのエージェントで比べる

## 問い

[Issue #234](https://github.com/yokozi-jp/agent-software-factory/issues/234) の調査。このリポジトリの開発環境を再現する方式（devcontainer、`doctor` の検査のスクリプト、skill、それらの組み合わせ）を、3 つの場面で比べる。

1. 新しく参加する人のマシン（Windows 11 の WSL2。今の Runbook は `docs/local-env-setup/setup.md`）。
2. 新しい git worktree で作業を始めるエージェント。
3. クラウドで動くエージェント（Kiro Web、Codex Cloud、GitHub Copilot cloud agent）。

結果は [#235 開発環境を再現する方式と、環境構築の skill を決める](https://github.com/yokozi-jp/agent-software-factory/issues/235) の材料にする。この文書は決定を下さない。`.env` と環境変数は [#215](https://github.com/yokozi-jp/agent-software-factory/issues/215)（`origin/research/env-management` の `research/env-management.md`）が扱うので、ここでは調べない。開発サーバーのポートは [#184](https://github.com/yokozi-jp/agent-software-factory/issues/184)、Playwright の Chromium は [#124](https://github.com/yokozi-jp/agent-software-factory/issues/124) にあるので、要点だけを引く。

調べた日は 2026-10-26。作業は WSL2 の Ubuntu 26.04、Kiro CLI 2.34.0、mise 2026.10.17、Docker Desktop（Docker Engine 29.9.1）、lefthook 2.2.2。実際にコマンドを動かして確かめた事実は「実行して確認」と書く。私の判断は「判断」と書く。クラウドのエージェントは 1 つも動かしていない（文書とコードだけ）。

## 要約

- devcontainer は [containers.dev の仕様](https://containers.dev/implementors/json_reference/) で書く。道具は Features（`ghcr.io/devcontainers/features/...`）で足し、`onCreateCommand`、`updateContentCommand`、`postCreateCommand` で依存を入れる。Features は `devcontainer-lock.json` で digest と checksum を固定できる。しかし、devcontainer を読むと仕様の一覧（[Supporting tools](https://containers.dev/supporting)）に載るのは VS Code、Codespaces、DevPod、Ona などで、Kiro、Codex Cloud、Copilot cloud agent は載っていない。Kiro IDE の devcontainer 対応は [kirodotdev/Kiro#164](https://github.com/kirodotdev/Kiro/issues/164) で open のまま。Kiro のエンジンのコードには devcontainer を読む処理が無い。
- testcontainers をコンテナの中から動かす方法は 2 つある。Docker-outside-of-Docker（ホストの socket を mount）と Docker-in-Docker（`privileged: true` のコンテナの中で dockerd を動かす）。Testcontainers の文書は DinD を「最後の手段」と書く。
- `doctor` の先例（`brew doctor`、`flutter doctor`、`mise doctor`）は、検査ごとに「何が足りないか」と「直すコマンド」を出し、問題があれば exit 1 にする。このリポジトリが使う道具も、それぞれ検査のコマンドを持つ（`mise doctor`、`vp env doctor`、`lefthook check-install`、`gh auth status`、`docker info`）。ただし `mise doctor` は、このリポジトリが意図して使わない `mise activate` を「problem」と判定して exit 1 になる（実行して確認）。
- クラウドのエージェントは、それぞれ自分の形式で環境を定義する。Copilot cloud agent は `.github/workflows/copilot-setup-steps.yml`（リポジトリの file で、変えると普通の workflow として実行される）、Codex Cloud は設定画面の Install script と Start skill、Kiro Web は自動の検出と設定画面（環境の定義の file は文書に無い）。3 つとも devcontainer を読むとは書いていない。
- Docker と testcontainers: Copilot cloud agent は GitHub Actions の runner で動くので Docker がある。Codex Cloud と Kiro Web は、Docker が使えるかを文書に書いていない。Kiro のローカルの command sandbox（Linux の bubblewrap）は `/var/run/docker.sock` を隠すので、sandbox を有効にすると、エージェントの shell から testcontainers は動かない（エンジンのコードで確認）。
- TLS 検査: このマシンの Docker Desktop のコンテナは、ホストの信頼ストアを引き継がない。Zscaler が検査する host（`vite.plus`、`kiro.dev`、`www.google.com`）には `SELF_SIGNED_CERT_IN_CHAIN` で失敗し、ルート CA を mount して `NODE_EXTRA_CA_CERTS` に渡すと通った（実行して確認）。`registry.npmjs.org`、`pypi.org`、`mise.jdx.dev`、Docker Hub は今は検査の対象外で、CA なしでも通った。
- worktree: mise の道具は利用者ごとの共有の場所に入るので、新しい worktree で入れ直しは要らない（`mise ls --current --missing` は空、実行して確認）。`pnpm install --frozen-lockfile` は worktree ごとに要り、`worktree.sh add` が行う（約 6 秒）。Kiro CLI の workspace の信頼は folder の path の hash ごとに保存されるので、新しい worktree は信頼していない folder として扱われ、対話の V3 session では最初に「Trust this workspace?」が出る。

## 現状のリポジトリ（事実）

- Runbook は `docs/local-env-setup/setup.md` の 1 つ。Windows 側で `.wslconfig` と Docker Desktop の WSL Integration を設定し、Ubuntu 側で 2 つのブロック（apt、gh、mise、Vite+、Git の設定 / `gh auth`、clone、`mise install --locked`、`vp env install`、`pnpm install`、`pnpm check && pnpm test && pnpm build`）を貼り付ける。最後に `mise ls --current --missing`、`node -v`、`pnpm -v`、`pnpm exec nx show projects` を実行して、表示を目で確かめる。この確認は doctor の検査に近いが、期待する値をコメントに書いているだけで、失敗しても止まらない。
- 道具の版: CLI ツールは `mise.toml` と `mise.lock`（ADR 0009）、Node.js と pnpm は Vite+（`.node-version`、`package.json`）、npm の依存は `pnpm-workspace.yaml` の catalog。`mise.toml` は `[tools]` と `[settings]` だけで、ADR 0009 は tasks、環境変数、Node.js、pnpm を書かないと決めている。
- Git hook は lefthook（ADR 0001）で、`pnpm install` の `prepare` が入れる。hook は全ての worktree で共有される（`docs/tooling/worktrees.md`）。
- testcontainers: `apps/api/test/global-setup.ts` が `postgres:17` と `quay.io/keycloak/keycloak:26.8.1` を起動する。WireMock と S3Mock はまだ使っていない（`pnpm-workspace.yaml` の catalog に無い）。CI（`ubuntu-26.04`）は runner の Docker をそのまま使う（`docs/tooling/commands.md`）。
- CI の環境の作り方は `.github/workflows/ci.yml` にある。`voidzero-dev/setup-vp` で Node.js と pnpm、`jdx/mise-action` と `MISE_LOCKED=1` で CLI ツールを入れる。
- worktree: `tools/scripts/sh/worktree.sh add <branch>` が、`<main>-worktrees/<branch>` に origin/main から worktree を作り、`pnpm install --frozen-lockfile` まで行う。この調査の worktree の作成は 8.2 秒、そのうち `pnpm install` は 5.8 秒だった（実行して確認）。
- Kiro の hook（`.kiro/hooks/session-start.json`、`pre-tool-use.json`）は `node tools/scripts/src/hooks/...` を呼ぶ。動くには Node.js と、そのリポジトリの checkout が要る。
- `.devcontainer/` も `copilot-setup-steps.yml` も、doctor の script も無い。

## 方式ごとの事実

### A. devcontainer

標準の書き方:

- `.devcontainer/devcontainer.json` に `image`（または `build.dockerfile`、`dockerComposeFile`）、`features`、lifecycle の command を書く。lifecycle は `initializeCommand`（ホストで実行）→ `onCreateCommand` → `updateContentCommand` → `postCreateCommand` → `postStartCommand` → `postAttachCommand` の順。`onCreateCommand` と `updateContentCommand` は、クラウドのサービスが prebuild に使うので、利用者の secret を前提にしない。どれかが失敗すると、後の command は実行されない（[devcontainer.json reference](https://containers.dev/implementors/json_reference/)）。
- base image: `mcr.microsoft.com/devcontainers/base:ubuntu26.04`（`resolute`）がある。`dev-` の image はその場で更新されるので、再現性のために固定するよう README が書く（[devcontainers/images の base-ubuntu](https://github.com/devcontainers/images/tree/main/src/base-ubuntu)）。
- Features の版と中身は `devcontainer-lock.json`（`devcontainer.json` と同じ folder）に、`version`、`resolved`（sha256 の digest）、`integrity` で記録する（[lockfile の仕様](https://github.com/devcontainers/spec/blob/main/docs/specs/devcontainer-lockfile.md)）。`devcontainer outdated` と `devcontainer upgrade` が lockfile を扱う（[devcontainers/cli](https://github.com/devcontainers/cli)）。
- mise は `mise generate devcontainer` で雛形を出せる。出力は `mcr.microsoft.com/devcontainers/base:ubuntu`、Feature `ghcr.io/devcontainers-extra/features/mise:1`、`postCreateCommand: "mise install"`（mise 2026.10.17 で実行して確認、[docs](https://github.com/jdx/mise/blob/main/docs/cli/generate/devcontainer.md)）。この雛形は `--locked` を付けず、Vite+ も入れないので、このリポジトリでは書き換えが要る（判断）。
- Renovate の `devcontainer` manager は `image` と `features` の版を更新する（[Renovate の devcontainer manager](https://github.com/renovatebot/renovate/blob/main/lib/modules/manager/devcontainer/readme.md)）。`devcontainer-lock.json` を更新するかは確かめていない。
- CI で同じ devcontainer を build して command を実行するには [devcontainers/ci](https://github.com/devcontainers/ci) の action か `devcontainer up` と `devcontainer exec` を使う。

testcontainers を devcontainer の中で動かす方法:

| 方法                                                             | 仕組み                                                                                               | 制約                                                                                                                                                          | 出典                                                                                                                    |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Docker-outside-of-Docker（`docker-outside-of-docker:1`、1.10.1） | ホストの `/var/run/docker.sock` を `/var/run/docker-host.sock` に bind mount し、Docker CLI を入れる | ホストと同じ CPU アーキテクチャ。workspace の外の bind mount ができない（ホストの path を使う必要がある）。起動した container はホストの dockerd の兄弟になる | [README](https://github.com/devcontainers/features/tree/main/src/docker-outside-of-docker)、`devcontainer-feature.json` |
| Docker-in-Docker（`docker-in-docker:4`、4.1.3）                  | container の中で dockerd を動かす。`/var/lib/docker` を container ごとの volume に置く               | `privileged: true` が要る。ホストと同じ CPU アーキテクチャ                                                                                                    | [README](https://github.com/devcontainers/features/tree/main/src/docker-in-docker)、`devcontainer-feature.json`         |

- Testcontainers は、container の中から使う「sibling container」の形を正式に書いている。socket を mount し、Testcontainers が container の中にいることを検出して、`localhost` の代わりに default gateway の IP を使う。Docker Desktop では `TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal` が要る。DinD は「最後の手段」と書く（[Patterns for running tests inside a Docker container](https://java.testcontainers.org/supported_docker_environment/continuous_integration/dind_patterns/)）。Node 版の設定の変数は `TESTCONTAINERS_HOST_OVERRIDE`、`TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE`、`TESTCONTAINERS_RYUK_DISABLED`、`TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX`（社内の registry の mirror）など（[testcontainers-node の configuration.md](https://github.com/testcontainers/testcontainers-node/blob/main/docs/configuration.md)）。
- Testcontainers Cloud は、agent が SSH tunnel でクラウドの dockerd につなぎ、container をクラウドで動かす。CI では `TC_CLOUD_TOKEN` を渡して agent を起動する（[Testcontainers Cloud docs](https://testcontainers.com/cloud/docs/)、[testcontainers-cloud-setup-action](https://github.com/AtomicJar/testcontainers-cloud-setup-action)）。無料の枠は desktop で 1 回限りの 50 分で、CI は 1 つの service account で同時に 1 session（同じ docs の FAQ）。Docker が無い環境でも testcontainers を動かせる手段だが、有料のサービスと token が要る。

TLS 検査のある社内ネットワーク:

- 実行して確認: Docker Desktop の `node:24-slim` から `fetch("https://vite.plus/")` は `SELF_SIGNED_CERT_IN_CHAIN` で失敗した。`-v /usr/local/share/ca-certificates/CapgeminiPKIRootCA.crt:/ca.crt:ro -e NODE_EXTRA_CA_CERTS=/ca.crt` を付けると 200 になった。container はホストの信頼ストアを引き継がない。
- 実行して確認: 検査されるかは host ごとに違う。`openssl s_client` の発行者は、`www.google.com`、`kiro.dev`、`vite.plus` が Capgemini（`ztnzia-internet.capgemini.com`）、`registry.npmjs.org`、`pypi.org`、`mise.jdx.dev`、`mise.run`、`registry-1.docker.io`、`docs.docker.com` は本来の CA だった。対象外の一覧は Zscaler 側の設定で、変わりうる。
- devcontainer では、CA をホストから渡す仕組みを自分で書く必要がある（`mounts` と `containerEnv`、または image の `update-ca-certificates`）。仕様に CA を渡す専用の property は無い（判断。reference に該当する property が無いことによる）。mise は OS の信頼ストアを使い、`SSL_CERT_FILE` を設定すると OS の store を置き換える（追加ではない）。Node.js には `NODE_EXTRA_CA_CERTS` が別に要る（[mise の FAQ: TLS certificates](https://github.com/jdx/mise/blob/main/docs/faq.md)）。

### B. doctor の検査のスクリプト

先例:

- 実行して確認: このマシンで `mise doctor` は exit 1。problem は「mise is not activated」の 1 つで、このリポジトリは `mise exec` で道具を呼ぶので activate を要らないとしている（`setup.md`）。そのまま束ねると、問題のない環境が失敗になる。

- このリポジトリで検査する候補（判断。`setup.md` の確認の手順と、この調査で見つけた失敗から選んだ）:
  - 道具: `mise ls --current --missing` が空、`node -v` が `.node-version` と一致、`pnpm -v` が `package.json` の `packageManager` と一致、`lefthook check-install`。
  - GitHub: `gh auth status`、`git config --get credential.https://github.com.helper`（`gh auth setup-git` の結果）。

  - worktree: 自分が worktree の中にいるか、`node_modules` があるか、`.kiro/hooks` の command が動くか。
  - 時期が来たら: Playwright の Chromium の依存（#124）、開発サーバーのポートが空いているか（#184）。
- 置き場所: ADR 0024 は script を `tools/scripts` の TypeScript で書き、Node.js の型の除去で直接実行すると決めている。doctor の script もこれに従うことになる（判断）。ただし、Node.js が入る前の検査（mise、Vite+、gh が無い）は TypeScript では書けないので、その部分は sh か、Runbook の手順のままになる。

### C. skill

- このリポジトリの skill は `.kiro/skills/` と `.agents/skills/` にあり、`skills-lock.json` が出どころと hash を記録している。
- skill はリポジトリと一緒に運ばれる。Kiro の cloud session では `.kiro/` の steering、agent、hook、MCP が clone と一緒に効く（[Cloud sessions](https://kiro.dev/docs/cloud-sessions.md) の Configuration in the cloud）。Codex Cloud は「リポジトリにある skill は cloud task で使える」と書く（[Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments.md) の Current limitations）。Copilot cloud agent は `.github/skills/`、`.claude/skills/`、`.agents/skills/` の skill を読む（[About agent skills](https://docs.github.com/copilot/concepts/customizations/agent-skills)、[Adding agent skills](https://docs.github.com/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills)）。
- skill は文章なので、それだけでは何も検査しない。手順が古くなっても失敗しない。skill が doctor の script を呼び、失敗したら直し方を読む形にすると、検査は script が持ち、skill は「いつ、どの順で呼ぶか」と「失敗の読み方」を持つ（判断）。
- 先例: Codex Cloud の Start skill は「service を起動して、準備ができたかを確かめる手順」を、Install script と別に文章で持つ（同上の Customize installation and startup）。Kiro Crew は troubleshooting を `kirocrew doctor` から始めるよう書く（[kiro.dev/llms.txt](https://kiro.dev/llms.txt) の Crew Troubleshooting）。

## 場面ごとの事実

### 1. 新しく参加する人のマシン（Windows 11 の WSL2）

- 今の Runbook は、Docker Desktop を前提にして、WSL の Ubuntu に道具を直接入れる。Kiro IDE の devcontainer 対応の要望は [kirodotdev/Kiro#164](https://github.com/kirodotdev/Kiro/issues/164)（open、label `keep-open`、2026-10-26 に確認、コメント 57 件に maintainer の回答は無い）。Issue の本文は、VS Code の Dev Containers 拡張機能が proprietary で Kiro では使えないことを前提に書いている。Kiro CLI は Linux で動く（このマシンの WSL で 2.34.0 が動いている）ので、container の中に入れれば使える（判断。container の中で動かしてはいない）。
- devcontainer を WSL2 で使うと、Docker Desktop の上で container を作り、その中に道具を入れる。道具の版の正本が `mise.toml` と `devcontainer.json`（base image と Features）の 2 か所になる。`postCreateCommand` で `mise install --locked` と `vp env install` を実行すれば、道具の版は `mise.toml` のままにできる（判断）。
- devcontainer の中で testcontainers を動かすには、上の DooD か DinD が要る。Docker Desktop では `TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal` が要る（Testcontainers の docs）。WSL に直接入れる今の形では、どちらも要らない。
- TLS: WSL の Ubuntu には CA が入っている（`/usr/local/share/ca-certificates/`、`NODE_EXTRA_CA_CERTS`）。devcontainer にすると、その CA を container に渡す手順が増える（上の実行の結果）。
- Runbook との食い違い: 今の `setup.md` の確認は目視なので、手順が古くなっても気づくのは次に参加する人。doctor の script があれば、Runbook の最後の手順を「doctor を実行し、全て OK になること」にでき、CI でも同じ script を実行できる（判断）。

### 2. 新しい git worktree で作業を始めるエージェント

- 依存: mise の道具は `~/.local/share/mise` に入り、worktree の間で共有される。新しい worktree でも `mise ls --current --missing` は空で、`mise exec -- shellcheck --version` は 0.11.0 を返した（実行して確認）。`[tools]` だけの `mise.toml` は `mise trust` を要らない（ADR 0009）。`node_modules` は worktree ごとに要り、`worktree.sh add` が `pnpm install --frozen-lockfile` を行う。
- ポート: Vite は塞がっていると次のポートで起動し、API は失敗する。worktree ごとの割り当ては #184 で扱う。
- Kiro の workspace の信頼: 信頼の答えは `~/.kiro/workspace-roots/<hash>/permissions.yaml` の `workspaceTrusted` に保存される（[Permissions: Workspace trust](https://kiro.dev/docs/permissions.md)）。hash は workspace の root の path の sha256 の先頭 16 文字（エンジン `acp-server.js` の関数 `Tw`）。計算すると、main の作業ツリーは `64f12cae82d16915`（`workspaceTrusted: true` が保存済み）、この worktree は `cfe81e469035ea35`（保存なし）だった（実行して確認）。worktree ごとに path が違うので、信頼は worktree ごとに要る。
  - 対話の V3 session（Kiro CLI 2.33 以降）は、最初に「Trust this workspace?」を出す。2.34 以降は `--trust-workspace` でその起動だけ信頼できる（保存しない）。`--no-interactive` と V1、V2 は聞かずに読み込む（同上）。
  - 信頼していない workspace では、Kiro は workspace の custom agent、steering、MCP、skill を読み込まず、shell の command ごとに確認を求める。hook の実行も止まる（エンジンが `hooks.v2.executionDisabledUntrustedWorkspace` を log に出す。`acp-server.js` の hook の module）。このリポジトリの SessionStart と PreToolUse の hook（force push の拒否など）も、信頼するまで動かない。
- 先例: Codex の desktop app の Local environments は、worktree を作ったときに自動で実行する setup script を `.codex` の folder に置き、リポジトリに commit できる（[Local environments](https://learn.chatgpt.com/docs/environments/local-environment.md)）。このリポジトリでは `worktree.sh add` が同じ役割を持つ。
- Kiro のローカルの command sandbox（Kiro CLI 2.31 以降、既定は off）を有効にすると、bubblewrap が `/var/run/docker.sock` を隠す（`acp-server.js` の bubblewrap の引数の組み立てで、`hideFileIfExists("/var/run/docker.sock")`）。`/autonomous on` は sandbox を強制し、外への通信を止めて始める（[Local command sandbox](https://kiro.dev/docs/sandbox.md)）。この状態では、エージェントの shell から testcontainers の test（`api` の integration）は動かない。sandbox の backend の `docker` は「not yet implemented」で、noop に戻る（同じ file）。

## 手順が Runbook と食い違うのを防ぐ方法

- 正本を 1 つにして、他から呼ぶ。道具の版は今も `mise.toml`、`mise.lock`、`.node-version`、catalog が正本で、Runbook と CI はそれを読むだけ（ADR 0009）。devcontainer の `postCreateCommand` や `copilot-setup-steps.yml` も、版を書かずに `mise install --locked` と `vp env install` を呼べば、版は増えない（判断）。
- 検査を実行できる形にする。doctor の script は CI で実行できる。`copilot-setup-steps.yml` は変わると普通の workflow として実行される（Copilot の docs）。devcontainer は `devcontainers/ci` で build して test できる。skill と Runbook の文章は、実行できないので食い違いを自動では見つけない。
- 先例の ADR 0009 は、版を 4 か所に手で書いていて、上げるたびに 4 か所を変えていたことを、mise に寄せた理由に挙げている。環境の定義を方式ごとに増やすと、同じ形の重複が戻る（判断）。

## 決定への材料（#235 へ）

選択肢と trade-off を挙げる。決めるのは #235。

1. **今の Runbook を残し、doctor の script を足す。** Runbook の最後の確認を `doctor` の実行に置き換え、CI でも実行する。worktree は `worktree.sh add` の後に呼ぶ。クラウドのエージェントは、それぞれの setup の後に呼ぶ。
   - 得るもの: 版の正本は増えない。WSL2、worktree、クラウドの全てで同じ検査を使える。ADR 0024 の形（`tools/scripts` の TypeScript）に乗る。
   - 失うもの: 環境を作るのは今の手順のまま。Node.js の前の段階（mise、Vite+、gh）は TypeScript で検査できない。何を doctor が検査するか（Docker、CA、ポート）を決める必要がある。`mise doctor` をそのまま束ねると、activate していないことで失敗する。
2. **1 に加えて、doctor を呼ぶ環境構築の skill を置く。** skill は「いつ doctor を呼ぶか」「失敗をどう直すか」「クラウドのエージェントで setup に何を書くか」を持つ。
   - 得るもの: 3 つのクラウドのエージェントがリポジトリの skill を読む。失敗の直し方を、エージェントが読める形で残せる。
   - 失うもの: skill の文章は検査されないので、doctor の出力と食い違いうる。Kiro では、worktree を信頼するまで skill は読み込まれない。
3. **1 に加えて、`copilot-setup-steps.yml` を足す（Copilot を使うなら）。** CI の `setup-vp` と `mise-action` の step を写し、最後に doctor を呼ぶ。
   - 得るもの: リポジトリに置け、変更時に workflow として検査される唯一のクラウドの定義。Docker があるので testcontainers も動く。
   - 失うもの: CI と step が重複する（composite action に切り出すかの判断が要る）。Copilot を使わないなら不要。
4. **devcontainer を足す。**
   - 得るもの: VS Code と Codespaces と DevPod では標準の形。CI で同じ container を build できる。
   - 失うもの: Kiro IDE、Kiro Web、Codex Cloud、Copilot cloud agent のどれも devcontainer を読むと書いていないので、3 つの場面のどれでも主な利用者に効かない。testcontainers のために DooD か DinD が要る。社内の CA の mount を自分で書く。base image と Features の版が、mise とは別の正本になる。
5. **クラウドでの testcontainers を Testcontainers Cloud に任せる。**
   - 得るもの: Docker の無いクラウドの sandbox でも integration test を動かせる可能性がある。
   - 失うもの: 有料のサービスと token。token をエージェントの環境に渡すことになる（Kiro Web の docs は secret が漏れうると書く）。Docker の無い環境で agent が動くかは確かめていない。

次の点を #235 で決める候補として挙げる。

- doctor の検査の範囲（道具、gh、Docker、CA、worktree、Kiro の信頼、ポート）と、問題と警告の線引き（`flutter doctor` の `missing` と `partial` の違いに当たる）。
- doctor を呼ぶ場所（Runbook の最後、`worktree.sh add`、SessionStart hook、CI、クラウドの setup）。SessionStart hook は timeout が 10 秒なので、Docker の pull のような遅い検査は向かない（判断）。
- Kiro の信頼を worktree ごとにどう扱うか（毎回「Trust」を選ぶ、`--trust-workspace` を使う、`~/.kiro/workspace-roots/` に書く script を作る）。最後の案は、Kiro が「リポジトリが自分の信頼を変えられない」ようにしている設計を回り道するので、避けるべきかを決める（判断）。
- どのクラウドのエージェントを使うか。Kiro Web で Docker が使えるかは、実際に 1 回動かして確かめる必要がある。
- devcontainer を「足さない」と決めるなら、その理由を ADR に残すか。

## 確かめられなかったこと

- Kiro Web と Codex Cloud の sandbox で、Docker（testcontainers）が使えるか。文書に記述が無く、実際には動かしていない。
- Kiro Web が「Dockerfile から環境を作る」（製品 page の記述）の具体的な手順と、どの Dockerfile を読むか。docs に記述が無かった。
- Kiro Web の「setup commands」の設定の場所。
- Copilot cloud agent の firewall が、Docker の container（testcontainers が起動するもの）の通信にかかるか。
- Renovate の devcontainer manager が `devcontainer-lock.json` を更新するか。
- Docker Desktop の dockerd が image の pull で社内の CA を信頼するか。今は Docker Hub と `quay.io` が TLS 検査の対象外で、試せなかった。
- Testcontainers Cloud の agent が、このマシンの TLS 検査の下で動くか。
